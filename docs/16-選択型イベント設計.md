# 選択型イベント設計

[グラフィック設計](./08-グラフィック設計書.md)・[ユニット設計](./12-ユニット設計.md)（§13 将来拡張）を引き、経済を「生産（任務）主導」から「**イベントと選択主導**」へ転換する設計。参照元は *60 Seconds!*（Robot Gentleman）だが、**このゲームの核は変えない**——核とは [README](./README.md) の一文「今日を生き延びるために備蓄を使うか、明日のために温存するか」に象徴される**備蓄の緊張**である。イベントはこの循環を回し/脅かす存在として導入する。

---

## 0. 背景と目的

### 現状の問題（実測から）

- 経済が**生産（任務）主導**。リソースは任務から得られ、イベントは ±5–25 の修飾子に過ぎない。
- 結果、生存率は**生産スキル**で決まる。sim で熟練（おまかせ配置）と無作為の差が 70 点以上開き、イベント影響量を増やしても埋まらない（生産力差が支配）。
- `autoAssign`（貪欲なおまかせ）が事実上の最適解で、プレイヤーが自分で配置する理由が薄い。
- 難易度のレバーが `road coef`（食料生産）一本に集中し、0.1 の変更で生存率が 25 点揺れる**ナイフエッジ**。

### 目的

- **イベントを資源フローの主軸**にする。任務は生活のベースライン維持、資源の動的な増減はイベントと選択から生まれる。
- **選択に意味を持たせる**。「交易・探索・危機の選択」などの判断が 30 日の生死を左右する。
- **運（イベントの下振れ）が本当に効く**ようにする。良いプレイは勝率を最大化するが保証しない。
- **核（備蓄の緊張）は維持・強化**する。イベントは備蓄・士気・炊き出しの循環を主戦場にする。

### 設計原則

1. **核を変えない**: 任務配置と備蓄の緊張は残す。イベントはそれを**置き換える**のでなく**支える/揺さぶる**。
2. **イベントは二軸**: 自動イベント（既存・背景の分散）と選択イベント（新・資源の主フロー）を分けて設計する。
3. **選択イベントはイベント発生型**: 「毎日選ぶ日報メニュー」にはしない。高頻度で**起きる出来事への対応**とし、生産最適化への退化（リソース管理の形骸化）を避ける。
4. **備蓄に収束させる**: 選択イベントの多くは備蓄・士気に作用し、「備蓄を得る/守る/使う」の判断に帰着させる。
5. **純粋・決定的を保つ**: 選択は `commitDay` と同列の**入力アクション**。乱数と選択入力が同じなら同じ結果。

## 1. イベント二軸モデル

| 軸 | 既存/新 | 解決 | 頻度 | 役割 |
| --- | --- | --- | --- | --- |
| **自動イベント** | 既存 | 自動（`apply`/`mutate`） | 1件/日 | 背景の分散（発電機故障・感染症・天候 等） |
| **選択イベント** | 新 | プレイヤーが選択肢から決定 | 高頻度（ほぼ毎日1件） | 資源の主フロー、意味のある判断 |

- 1日あたりの解決順: **任務効果 → 清算（settlement）→ 自動イベント → 選択イベント**。
- 選択イベントは発火すると解決を**一時停止**し、プレイヤーの入力を待つ（§2）。
- 自動イベントと選択イベントは別プール・別抽選。選択イベントの発生確率は高く（例: 70–90%）し、「ほぼ毎日起きる出来事」にする。ただし**どのイベントが起きるか・選択肢の結果は運**に左右される。

## 2. コアループと決定フェーズ（case A）

`step()` は純粋同期のまま、選択イベントで**一時停止**する。

### 2.1 フェーズとアクション

```ts
type Phase = 'planning' | 'choice' | 'ended'

type Action =
  | { type: 'commitDay'; plan: DayPlan }
  | { type: 'resolveChoice'; optionId: string }
```

- `commitDay`: 任務 → 清算 → イベント解決を開始。選択イベントに達したら `phase: 'choice'` で**停止**。
- `resolveChoice`: 選んだ選択肢を適用し、残りのイベント解決を**再開**。全て解決したら日付進行・終了判定。

### 2.2 状態の拡張

解決を再開可能にするため、その日の未解決イベントキューと保留中の選択を `GameState` に持つ:

```ts
interface PendingChoice {
  eventId: string
  options: ChoiceOption[]   // 条件で絞られた利用可能な選択肢
}

interface GameState {
  // ...既存
  phase: Phase
  pendingEvents?: string[]      // その日の未解決イベントIDキュー（解決中にのみ存在）
  pendingChoice?: PendingChoice // 保留中の選択（phase === 'choice' のとき）
}
```

- `commitDay` 時に rng でその日のイベント（自動+選択）を確定し `pendingEvents` に積む。
- キューを先頭から処理。自動イベントは即適用、選択イベントは `pendingChoice` を設定して `phase: 'choice'` で返す。
- `resolveChoice` は `pendingChoice` の該当 option を適用、キューの残りを処理し、尽きたら日を確定。
- **決定性**: イベント確定も選択肢抽選も rng 由来。選択は入力。よって「同じ seed + 同じ選択 = 同じ結果」が保たれる。
- `pendingEvents`/`pendingChoice` は解決中の一時データ。日確定で消える。セーブは `phase: 'choice'` 中でも可能（保留状態を永続化、`SAVE_VERSION` 引き上げ）。

### 2.3 再生（usePlayback）との整合

- 現在: `commitDay` → busy（ビート再生: flow/event/arrival）→ 完了。
- 変更: 再生中に選択イベントに達したら**ポーズ**し、選択オーバーレイを表示。プレイヤーが選ぶと `resolveChoice` で再開。
- スポットライト機構（既存の arrival ポーズ）と同型。選択イベントも「ポーズ + カード + 選択 + 続行」。

## 3. 選択イベントDSL

`EventDef` を拡張する。既存の自動イベント互換は保つ。

```ts
interface ChoiceOption {
  id: string
  label: string                 // ボタン文言
  desc?: string                 // 補足（結果の示唆）
  when?: (ctx: EvalContext) => boolean  // 選択肢の出現条件
  apply?: (ctx: EvalContext) => Effect[] // 資源効果
  mutate?: (state: GameState) => { state: GameState; effects: Effect[] } // 状態変更（ユニット増減・負傷等）
}

interface EventDef {
  id: string
  name: string
  kind?: 'auto' | 'choice'   // 新規（省略時は 'auto'）
  once?: boolean
  when: (ctx: EvalContext) => boolean
  weight: (ctx: EvalContext) => number
  apply?: (ctx: EvalContext) => Effect[]       // auto
  mutate?: (state: GameState) => {...}         // auto
  choices?: ChoiceOption[]                     // choice（kind: 'choice' のとき必須）
}
```

- `kind: 'choice'` のイベントは発火時、`choices` を `when` で絞って `pendingChoice` にセット。
- プレイヤーが option を選ぶと、その `apply`/`mutate` を実行。
- 選択肢は2–3個を基本（「応じる/断る」「誰を出すか/出さないか」等）。

## 4. 選択イベントの類型

> **到着（arrival）は強制加入を維持**する（選択化しない）。受入/拒否の分岐は枝を増やすだけで核に寄与しないと判断し、採用しない。選択イベントは以下の3類型。

### 4.1 交易（trading）

行商人・近隣集落が資源交換を提案。

- 例: 「食料20を予算15で売ろう」/「備蓄10と医療15を交換しないか」
  - **応じる**: 資源を交換（状況により得/損）。
  - **断る**: 変化なし。
- 資源間の**弁（トレード）**を作り、状況判断を促す。備蓄を絡めた取引（備蓄↔食料/医療）を重視。

### 4.2 探索の機会（expedition）— 資源供給の主軸

「今なら近隣を探索できる」という**機会イベント**として発生（常設の日報メニューではない）。**全ユニットが非探索中のときのみ発生**（探索の連鎖はしない）。

- **送出**: ユニットを1人選ぶ。送出時に**備蓄を前払い**（`cost`）し、そのユニットは**数ターン不在**になる（任務配置不可・不在中は食料消費0＝持参備蓄で賄う）。
- **帰還**: 最短 `minDays` 日後から**毎日抽選**。帰還率は日を追うごとに上昇（`returnBase + 経過日数×returnPerDay`、上限 `returnCap`）。帰還タイミングはランダム。
- **成果**（帰還時に適性で決定。`skill = 最大適性/10`、低適性→高適性で線形補完）:
  - **大成功**（低適性5%→高適性10%）: 平均**4日分**の資源（食料+備蓄+予算）。
  - **成功**（低適性30%→高適性60%）: **1日分**の資源（食料中心）。
  - **危険**（低適性25%→高適性10%）: 負傷（効果半減）または死亡（危険内の `deathShare`）。
  - **失敗**（残り）: 収穫なし。
  - 報酬は `最大適性×rewardCoef` を1日分とし、**帰還日数ボーナス**（不在が長いほど増）と**ランダム分散**（×0.7〜1.3）を掛ける。
- **怪我・死亡は既存の清算を再利用**（負傷=効果半減・医療で回復、死亡=ユニット除去・casualties加算・士気低下）。
- 探索の成果（とくに備蓄・食料）が炊き出し→士気の循環を回す燃料になる（§5）。

### 4.3 危機の選択（crisis）

資源間のトレードオフを強制する踏み絵。

- 例: 「発電が止まりそうだ。医療の電力を回すか？」（医療- / 電力+）
- 例: 「備蓄が傷みかけている。今すぐ配るか、捨てるか」（士気+ / 備蓄-）。
- 「備蓄を使うか温存するか」の核を、イベントとして直接突きつける。

## 5. 資源経済の再設計（核の強化）

**核（備蓄・士気・炊き出しの循環）を強くする**。イベント主軸化と核の強化は両立する——イベントがこの循環の燃料（備蓄）と脅威（士気）を動かすため。

### 5.1 士気低下の罰を強化（新規てこ）

現状、士気は <20 で離脱・0 で崩壊だが、生産に直結しない。士気を**生産を左右する資源**にし、炊き出し（備蓄→士気）を生命線にする。

- **低士気は作業効率を下げる**（任務効果に乗算）:
  | 士気 | 任務効果倍率 |
  | --- | --- |
  | ≧ 50 | ×1.0 |
  | 25–49 | ×0.85 |
  | < 25 | ×0.7 |
  （数値は sim で調整。`balance.ts` に集約）
- 離脱閾値の引き上げ（<20 → <25 等）も併用可。
- 効果: 士気を保たないと**生産が落ちる** → 炊き出し（備蓄→士気）が必須 → **備蓄が生命線**になる。

### 5.2 備蓄・炊き出しの重要性

- 備蓄の使い道: ① 炊き出し（士気回復）② 飢餓時の自動取崩（既存）。士気罰の強化で①が重くなる。
- 備蓄の**入手はイベント経由が主**（現状も hidden_stockpile 等が主）。選択イベントで備蓄を得る手段を増やす:
  - 探索（4.2）の成果
  - 交易（4.1）で備蓄を獲得
- 備蓄を**脅かす**イベントも置く（窃盗・襲撃・備蓄損傷）。「守る」判断を作る。

### 5.3 任務とイベントの役割分担

| | 任務（生産） | 選択イベント |
| --- | --- | --- |
| 位置づけ | 生活の**ベースライン維持** | 資源の**動的増減（主フロー）** |
| 性質 | 確実・低リターン | 変動・高リターン（リスク伴う） |
| プレイヤー | 配置の最適化 | 判断と運 |

- 任務係数は「維持が精一杯」に抑え、**surplus で勝ち切れない**ようにする（road ナイフエッジの解消）。
- 資源の上振れ/下振れはイベントが担う。生存 = ベースライン維持 + イベントの引き + 選択の良し悪し。

## 6. 探索バランスの指針

探索が「常に応得」になるとリソース管理が形骸化する（Q2 で指摘された点）。以下のバランスで抑制する:

- **負傷/死亡率**: 探索には実質的なリスク。とくに強力なユニットを失う損失は大きい（「誰をリスクに晒すか」の判断）。
- **報酬の分散**: 大漁/並/手ぶら/負傷を乱数で。安定した日給にしない。
- **頻度**: 高頻度だが毎日確定ではなく、また成果が毎回良いわけではない。
- **適性依存**: 適したユニットを出さないと成果が細い。「誰を出すか」に意味。
- 最終値は sim で確定。**熟練〜70% / 無作為〜1-2%**（イベント依存・硬派。全4エンディング到達可）。

## 7. UI/UX

- **選択オーバーレイ**: スポットライト（既存 arrival 演出）と同型。イベント名・状況文・選択肢ボタン（label + desc）。
- **ポーズ**: 再生中に選択で停止。選択すると続行。
- **結果表示**: 選択の結果（得た/失った資源、負傷・死亡）をレポート/ビートで表示。
- **探索の成果**: 成果（備蓄+X、負傷 等）をカードで明示。
- 詳細は [WebUI技術設計書](./07-WebUI技術設計書.md) に追記。

## 8. エンディング

- **当面は既存4エンディングを維持**（full_recovery / managed_sacrifice / self_governance / collapse）。選択イベントは資源・生死に影響し、間接的にエンディングを左右する。
- **イベントチェーン型のエンディングは採用しない**（分岐が増えるため、一旦見送り）。
- **将来拡張（別フェーズ）**: 30日の**成果**や**成績**で分岐する形。例:
  - 成果ベース: 「誰も死ななかった」/「◯人以上死んだ」/「特定のユニークがいる」等でエンディングが分岐。
  - 成績集計: プレイ結果（生存者数・死者数・資源・協力値等）を集計し、その結果に基づく評価/分岐。
  いずれも本設計のスコープ外。別途設計する。

## 11. リスク

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 選択イベントが日報メニュー化し生産最適化に戻る | 高 | イベント発生型を堅持（§0-3）。頻度は運、成果は分散 |
| 探索が「常に応得」でリソース管理が形骸化 | 高 | 負傷/死亡率・報酬分散・適性依存で抑制（§6） |

| 決定フェーズで純粋性/決定性が壊れる | 高 | 選択は入力アクション、rng と分離。決定性テストで保証 |

| 核（備蓄の緊張）が薄れる | 高 | イベントを備蓄・士気に収束（§5）。任務配置は維持 |

## 13. DoD（P1+P2 完了時）

- [ ] 選択イベントが発火し、オーバーレイで選択肢を選べる
- [ ] `resolveChoice` で解決が再開し、日が確定する（純粋・決定的、決定性テスト緑）
- [ ] 交易・危機・探索の各イベントが機能する（arrival は強制加入のまま）
- [ ] 探索イベントで備蓄/食料を得られ、負傷/死亡は既存清算（`condition`/`casualties`）で処理される
