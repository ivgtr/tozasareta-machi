# 実装計画: 孤立した町の30日間

設計書（01–10）を、実行可能なマイルストーン計画に統合する。領域ごとの実装順序（06 §13 / 07 §9 / 08 §8）は、ここでは全体最適のフェーズに組み直す。

---

## 0. 計画の原則

- **各フェーズは検証可能な状態で終える**。CI グリーン、または「動くもの」が必ずある。思いつきの追加はしない。
- **ヘッドレスファースト**: コアは純粋 reducer なので、**UI より先にゲームをヘッドレスで完成**させ、シミュレーションで面白さとバランスを検証する。これが本アーキテクチャ最大のレバレッジ。
- **リスクの早期解消**: 不確かな要素は設計で無害化する。タッチDnDはタップ+キーボードのフォールバックを必須要件にし、プレイバックはタイミングを定数化・スキップ必須にして、該当フェーズで早期検証する（スパイクは行わない）。
- **数値は後回し、道具は先**: バランス数値の確定は遅らせるが、シミュレーションの道具は早期に作り、調整を安くする。
- 見積もりは**相対サイズ（S/M/L）**。個人開発のためカレンダー見積もりはしない。

## 2. 依存関係とクリティカルパス

```
        P1 ──┬── P2 ── P3 ─┐
             │             ├── P5 ── P6 ── P7 ── P8 ── P9
             └── P4 ───────┘
```

- **クリティカルパス**: `P1 → P2 → P3 → P5 → P6 → P7 → P8 → P9`
- **並行の余地**: P4（UI基盤）は P1 のみに依存するため、**P2/P3 と並行可能**。2トラックで回すならここに載せる。
- P2 が最長（L）。ここが全体のボトルネックであり、最優先で着手・保護する。

## 3. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| タッチDnDが期待通り動かない | 高 | タップ+キーボードのフォールバックを設計要件化（07 §5）。P5 で3入力系を同時に実装・検証 |
| プレイバックの感触が悪い | 中 | タイミング定数を `ui-timing` に集約、スキップ機能必須。P6 で早期検証 |
| バランス破綻（簡単すぎ/無理ゲー） | 中 | P2 でsimの道具、P9 で調整。`BALANCE` を一元化（09 §7） |
| レトロパレットの可読性不足 | 中 | P4 でコントラスト実測、色単独伝達の禁止（10 §7） |
| スコープの膨張 | 中 | 10 §10 の非目標を盾にする。フェーズのゲートで区切る |
| 設計書と実装の乖離 | 中 | 設計に無い機能は出さない。必要なら先にドキュメントへ追記 |

## 4. 検証戦略

| 粒度 | 内容 |
| --- | --- |
| コミットごと | `lint + typecheck + test`（CI自動、緑をマージ条件） |
| フェーズごと | §1 のゲートを確認してから次へ |
| P2・P9 | シミュレーション出力（勝率・エンディング分布）をレビュー |
| リリース前 | デスクトップ + モバイルで手動フルプレイ |

勝率の目標（09 §9）: **無作為プレイで時々生き残る / 意図的プレイで安定勝利**。

---

## 5. 進め方の規律

- 1マイルストーン = まとめてレビューできる単位。CI グリーンなしで次へ進まない。
- **各フェーズの終わりにコミットする**（1フェーズ = 1コミット）。CI（typecheck/lint/format/test/build）がグリーンのときのみコミットし、複数フェーズの作業を混ぜない。
- 数値は必ず `balance.ts` へ。ロジックにマジックナンバーを書かない。
- 「思いついた機能」は実装せず、まず設計書へ追記して合意する（非目標 10 §10 を参照）。
- 各フェーズの終わりに、設計書との差分があればドキュメントへ反映する（コードを正にしない）。
