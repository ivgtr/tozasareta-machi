# 期間修正イベント設計

[選択型イベント設計](./16-選択型イベント設計.md) を引き、ランダムイベントに**期間にわたる状態変化**（Modifier）を導入する。目的はリプレイ時のランダム性と戦略的多様性の確保。既存の即時 delta イベントと共存し、自動イベントプールを拡充する。

---

## 0. 背景と目的

### 現状の問題

- 自動イベント20件はすべて**即時 delta**（resource ±N）。1日で完結し、翌日以降の判断に影響しない。
- リプレイ時の分岐が「どのイベントを引くか」の一点に依存し、**数日間の戦略変更**を迫るイベントがない。
- プレイヤーが「今日は台風だから屋内任務に集中する」「食料消費が止まる3日間に備蓄を温存する」のような**日程の再設計**をする場面がない。

### 目的

- **期間修正（Modifier）** を導入し、数日間にわたって経済・任務・消費を変えるイベントを実現する。
- 自動イベントのバリエーションを大幅に増やし（+22件）、リプレイごとの盤面差を広げる。
- 既存の即時 delta イベントと共存させる。期間修正は「特別な回」、即時 delta は「日常の分散」として役割分担する。

### 設計原則

1. **核を変えない**: 備蓄の緊張・任務配置の判断は維持。Modifier はそれを**揺さぶる**存在。
2. **純粋・決定的を保つ**: Modifier の発動・デクリメント・除去はすべて step 内で完結。同じ seed + 同じ行動 = 同じ結果。
3. **汎用的な機構にする**: 個別 kind の enum ではなく、ターゲット文字列 + 演算のクエリ型。将来の効果追加が型変更なしで済む。
4. **UI は後追い**: コア機構 → イベント定義 → UI 表示の順。M1–M2 はヘッドレスで検証可能。
5. **数値は balance.ts**: Modifier の日数・倍率・イベントの weight はすべて BALANCE に集約。

## 1. Modifier 機構

### 1.1 型定義

```ts
interface ModifierEffect {
  target: string
  op: 'mult' | 'add' | 'set'
  value: number
}

interface Modifier {
  id: string
  daysLeft: number
  startDay: number
  effects: ModifierEffect[]
}
```

`GameState` に追加:

```ts
interface GameState {
  // ...既存
  modifiers: Modifier[]
}
```

### 1.2 ターゲット命名規約

`{カテゴリ}:{対象}` の形式。カテゴリは参照箇所と対応する。

| カテゴリ | 対象例 | 参照箇所 | 意味 |
| --- | --- | --- | --- |
| `consume` | `food` | settlement（食料消費） | 消費量への倍率/上書き |
| `decay` | `power`, `medical` | settlement（自然減衰） | 減衰量への倍率 |
| `produce` | `repair_power`, `all` 等 | actions（任務産出） | 任務産出への倍率。0 = 配置不可 |
| `income` | `budget` | settlement（予算収入） | 収入への倍率 |
| `drain` | `stockpile`, `food` 等 | settlement（新規ブロック） | 毎日固定で加減（add 演算） |
| `chance` | `injury`, `desertion` | settlement（確率） | 発生確率への倍率 |

将来の拡張例: `event:weight`（イベント発生率）、`expedition:return`（帰還率）等。型変更なしで参照側を追加するだけ。

### 1.3 クエリ関数（`src/game/modifiers.ts`）

```ts
export function queryMult(mods: Modifier[], target: string): number {
  let result = 1
  for (const m of mods) {
    for (const e of m.effects) {
      if (e.target !== target) continue
      if (e.op === 'set') return e.value
      if (e.op === 'mult') result *= e.value
    }
  }
  return result
}

export function queryAdd(mods: Modifier[], target: string): number {
  let result = 0
  for (const m of mods) {
    for (const e of m.effects) {
      if (e.target === target && e.op === 'add') result += e.value
    }
  }
  return result
}

export function isTaskDisabled(mods: Modifier[], task: TaskId): boolean {
  return queryMult(mods, `produce:${task}`) === 0
}

export function tickModifiers(mods: Modifier[], day: number): Modifier[] {
  return mods
    .map((m) => (day > m.startDay ? { ...m, daysLeft: m.daysLeft - 1 } : m))
    .filter((m) => m.daysLeft > 0)
}
```

- `queryMult`: 全 mult を乗算。set があれば即座にその値を返す（set 優先）。
- `queryAdd`: 全 add を加算。drain 系に使う。
- `isTaskDisabled`: produce 系の実効値が 0 なら配置不可（UI と autoAssign が参照）。
- `tickModifiers`: 作成日（startDay）の翌日からデクリメント。0 で除去。

### 1.4 ライフサイクル

```
Day N: イベント発火 → mutate で modifier 追加（daysLeft: K, startDay: N）
Day N の finalizeDay: tickModifiers → startDay === day なのでデクリメントなし
Day N+1: 任務/清算で modifier が効く。finalizeDay で daysLeft K → K-1
Day N+K: finalizeDay で daysLeft 0 → 除去
```

`daysLeft: 2` なら「発火日の翌日から2日間」有効。

### 1.6 重複・衝突の規則

- **同一 id の modifier が既にある場合**: `daysLeft` を新しい値で上書き（延長）。effects は新しいものに置換。
- **異なる id で同じ target に set が複数**: 後に追加された modifier の set が優先（queryMult は配列順に走査し、set 命中時点で即 return）。
- **mult の重ねがけ**: 乗算で合成（例: volunteer_surge ×1.3 と sunny_stretch ×1.5 が別 target なら独立、同 target なら 1.95）。

## 2. イベントカタログ（+22件）

全イベントは自動イベント（`kind` 省略 = auto）。weight はプール内相対値。`when` 条件で日ごとに有効プールが絞られるため、実効確率は weight 単体では決まらない。

### 2.1 特大ラッキー（4件）

一度きり or 非常に稀。盤面を好転させるが、それだけで勝てるほどではない。

| id | 名前 | when | weight | 効果 |
| --- | --- | --- | --- | --- |
| `manna` | 恵みの雨 | day >= 10, once | 0.06 | modifier: `consume:food` set 0 / 3日。morale +5 |
| `supply_drop` | 救援物資の投下 | day >= 12, once | 0.07 | 即時: food +15, power +15, medical +15, stockpile +15 |
| `hot_spring` | 温泉の発見 | day >= 8, once | 0.05 | 即時: morale +20, medical +10 |
| `miracle_harvest` | 奇跡の収穫 | day >= 10, once | 0.06 | 即時: food +40, stockpile +15 |

設計意図:
- すべて once。30日中に0–1回。来ない盤面が普通。
- `manna` は期間修正の代表格。「食料消費0の3日間」に備蓄を温存する / 炊き出しを止めて任務に回す等の判断が生まれる。
- 即時系（supply_drop, hot_spring, miracle_harvest）は特大だが一回限り。持続的な優位にはならない。

### 2.2 ラッキー（6件）

中頻度。数日間のボーナスまたは即時の中程度リソース。

| id | 名前 | when | weight | 効果 |
| --- | --- | --- | --- | --- |
| `sunny_stretch` | 晴天続き | day >= 5, power < 80 | 0.20 | modifier: `produce:repair_power` mult 1.5 / 3日 |
| `animal_trap` | 獣の罠 | day >= 5 | 0.20 | 即時: food +20, stockpile +10 |
| `traveling_engineer` | 旅の技術者 | day >= 6 | 0.15 | modifier: `produce:reinforce_medical` mult 1.5 / 2日。morale +3 |
| `volunteer_surge` | ボランティア殺到 | day >= 6, morale >= 40 | 0.15 | modifier: `produce:all` mult 1.3 / 2日 |
| `clean_water` | 湧水の発見 | day >= 5, medical < 80 | 0.20 | 即時: medical +15, morale +5 |
| `cached_fuel` | 燃料の備蓄発見 | day >= 6, power < 80 | 0.20 | 即時: power +20, stockpile +10 |

設計意図:
- 期間修正系（sunny_stretch, traveling_engineer, volunteer_surge）は「この数日間はあの任務が強い」という一時的な方針変更を促す。
- 即時系（animal_trap, clean_water, cached_fuel）は既存の foraging / medical_donation / power_restored と同系統だが、やや弱め（+15–20 vs 既存 +26）。新規イベントの総量が増えるため、1件あたりの delta は抑える。

### 2.3 バッド（9件）

中〜高頻度。期間ペナルティまたは即時損失。既存バッド（road_collapse, infection 等）と合わせて圧力を形成。

| id | 名前 | when | weight | 効果 |
| --- | --- | --- | --- | --- |
| `typhoon` | 台風接近 | day >= 8 | 0.30 | modifier: `produce:repair_power` set 0, `produce:restore_road` set 0 / 2日。morale -3 |
| `storage_flood` | 備蓄庫の浸水 | day >= 7, stockpile >= 20 | 0.25 | 即時: stockpile -20, food -10 |
| `generator_overheat` | 発電機の過熱 | day >= 6, power > 30 | 0.25 | 即時: power -20。modifier: `produce:repair_power` set 0 / 1日 |
| `landslide_actual` | 地滑り発生 | day >= 10 | 0.25 | 即時: stockpile -15。ランダム1体負傷 |
| `food_spoilage` | 食料の腐敗 | day >= 7, food >= 30 | 0.25 | 即時: food -25 |
| `cold_snap` | 寒波 | day >= 12 | 0.25 | modifier: `decay:power` mult 1.5 / 3日。morale -3 |
| `rumor` | デマの拡散 | day >= 6, morale >= 30 | 0.20 | 即時: morale -12 |
| `rat_infestation` | ネズミの大量発生 | day >= 8, stockpile >= 15 | 0.25 | modifier: `drain:stockpile` add -10 / 3日 |
| `insomnia` | 集団不眠 | day >= 9, morale < 50 | 0.20 | modifier: `produce:all` mult 0.7 / 2日 |

設計意図:
- `typhoon` は期間修正バッドの代表。「屋外任務が2日止まる」間に電力・食料が溶ける。プレイヤーは台風前に修理を済ませる / 屋内任務に切り替える判断を迫られる。
- `cold_snap` は即時ではなく「3日間、電力の減衰が1.5倍」。repair_power の産出が追いつかなくなる持続圧。
- `rat_infestation` は drain 系。「毎日備蓄が10ずつ消える」は探索のコスト（12）と絡み、探索判断に影響する。
- `generator_overheat` は既存の `generator_failure`（power -32, 即時）と役割が被るが、こちらは「1日修理不可」の期間制約付き。即時大ダメージ vs 持続小制約の差。
- weight は既存バッド（road_collapse 0.4, infection 最大2.0）より抑えめ。新規期間ペナルティの重さを考慮。

### 2.4 連鎖（3件）

特定のイベント発生後に条件が緩和される。`flags` の既存カウンターを参照。

| id | 名前 | when | weight | 効果 |
| --- | --- | --- | --- | --- |
| `aftershock` | 余震 | day >= 8, flags.casualties >= 0, road_collapse 発生済み（flags.fired 参照不可のため resource 条件で近似: food < 60） | 0.35 | 即時: food -15, morale -5。modifier: `produce:restore_road` set 0 / 1日 |
| `second_wave` | 感染症の第2波 | day >= 12, medical < 25 | 0.35 | 即時: medical -15。ランダム1体負傷 |
| `gratitude` | 住民からの感謝 | morale >= 70 | 0.30 | 即時: budget +15, morale +5, cooperation +1 |

設計意図:
- 連鎖イベントは `flags.fired`（once イベントの発火記録）では参照できない（auto イベントは once でなければ fired に入らない）。そのため **resource 状態を代理条件**として使う。
- `aftershock`: road_collapse 後は food が下がる傾向があるため `food < 60` で近似。
- `second_wave`: infection 後は medical が低いため `medical < 25` で近似。
- `gratitude`: 高士気の報酬。volunteers / childbirth と相性がよく、好循環を強化する。

### 2.5 weight 設計の根拠

自動イベントは1日1件・有効プール内 weightedPick。既存20件 + 新規22件 = 最大42件だが、`when` 条件により日ごとの実効プールは10–25件程度。

| カテゴリ | weight 帯 | 30日中の期待出現 | 根拠 |
| --- | --- | --- | --- |
| 特大ラッキー | 0.05–0.07 | 0.3–0.7回 | once + 高 day 条件。来ない盤面が普通 |
| ラッキー | 0.15–0.20 | 2–4回 | 既存ラッキー（foraging 0.45）より低め。総量増加の調整 |
| バッド | 0.20–0.30 | 3–6回 | 既存バッドより抑えめ。期間ペナルティの重さで補償 |
| 連鎖 | 0.30–0.35 | 0–2回 | 条件付き。前提イベント次第 |

既存イベントの weight は変更しない。新規イベントの追加で実効プールが広がり、既存イベントの個別出現率は自然に下がる（希釈効果）。これは意図的: 1件あたりのインパクトが分散し、盤面が単調になりにくくなる。

## 3. balance.ts への追加

```ts
modifier: {
  manna: { days: 3 },
  sunny_stretch: { days: 3, mult: 1.5 },
  traveling_engineer: { days: 2, mult: 1.5 },
  volunteer_surge: { days: 2, mult: 1.3 },
  typhoon: { days: 2 },
  generator_overheat: { lockDays: 1 },
  cold_snap: { days: 3, mult: 1.5 },
  rat_infestation: { days: 3, drain: -10 },
  insomnia: { days: 2, mult: 0.7 },
  aftershock: { lockDays: 1 },
},
```

イベントの weight・即時 delta も balance.ts に集約するかは M2 実装時に判断。既存イベントが events-data.ts 内に直接書いているため、新規も同様に events-data.ts 内に記述し、期間（days）と倍率（mult）のみ balance.ts に集約する。

1. `types.ts`: `ModifierEffect`, `Modifier` 追加。`GameState.modifiers: Modifier[]`。

3. `settlement.ts`: §1.5 の表に従い参照点を挿入。drain ブロックを追加。
4. `actions.ts`: resolvePlacement / preview に produce クエリ挿入。autoAssign に disabled 除外。

8. テスト: modifier の生成・クエリ・tick・除去。settlement/actions への影響。決定性（同 seed で同結果）。

1. `DecisionBoard`: `isTaskDisabled` を参照し、disabled な任務スロットをグレーアウト + 配置不可。
2. `StatusWall` or `TopBar`: アクティブ modifier のバッジ一覧（id + 残り日数）。
3. `PlaybackOverlay`: modifier 発動/解除を flow ビートで表示。

### M4 詳細手順

1. `tests/simulation.test.ts`: modifier 統計のログ出力（イベント別発火回数 /game、modifier 有効日数 /game）。

3. sim 測定（random 40 / skilled 60）: **skilled 53% / random 3%**、全4END到達。目標（skilled〜50%、random 2–10%）の範囲内 → weight 調整は不要と判断。
4. 極端ケース検証: manna + volunteer_surge 同時発動、typhoon + cold_snap 同時発動等の重ねがけ。mult の合成は上限なしだが、同時発動確率が低く sim で崩壊は観測されなかった。

## 6. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| modifier の重ねがけで極端な盤面（例: produce:all ×1.3 ×0.7 = 0.91） | バランス崩壊 | M4 で同時発動ケースを sim 検証。mult の合成上限は設けないが、weight で同時発動確率を制御 |
| drain 系（rat_infestation）が探索コストと相殺 | 探索判断の歪み | drain は備蓄のみ。探索コストも備蓄なので影響するが、3日×10=30 は探索1回分（12）の2.5倍。許容範囲 |
| 有効プール42件で1件あたりの出現率が低下 | 既存イベントが体感できなくなる | 希釈は意図的。ただし sim で「30日間で既存バッドが0回」の盤面頻度を確認し、過度なら weight を底上げ |
| 連鎖イベントの代理条件（food < 60 等）が不正確 | 意図しないタイミングで発火 | M4 で発火タイミングの分布を確認。条件を調整 |
| UI の disabled 表示がわかりにくい | プレイヤーが配置して初めて弾かれる | M3 でグレーアウト + ツールチップ（「台風のため不可: あと1日」）を必須にする |
