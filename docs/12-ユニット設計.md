# ユニット設計: 孤立した町の30日間

「汎用作業員 + 別建ての人員（専任）」という二重システムを廃止し、**作業員そのものを名前・顔・能力を持つユニークユニット**へ置き換える設計。02/06/09 の「作業員・人員」に関する記述は本ドキュメントに置き換えられる。

---

## 1. 背景と狙い

旧システムの3問題を一挙に解決する。

| 旧システムの問題 | ユニット化による解決 |
| --- | --- |
| 作業員割り当て + 人員選択の二重操作が長い | 「誰をどこに置くか」の**一段**に統合 |
| 任務が似通って操作性が楽しくない | 任務が「誰で伸びるか」で個性化、ユニットも相互に異なる |
| 人員は適任が決まりきっていて選ぶ意味がない | 個性（適性・特性）が実際の効果差になり、配置がパズルになる |

副次効果: 名前と顔のある個人は**失いたくなる**（喪失リスクが愛着に変わる）。ランダム入手が毎プレイの盤面を変える。

---

## 2. 概要（コアループ）

1. **ロスター**: 4ユニットで開始。各自が4適性 + 0〜2特性 + 状態を持つ。
2. **配置**: 毎日、各ユニットを1任務に置く（複数配置可・合算）か待機。
3. **解決**: 任務効果 = 基礎値 + 配置ユニットの該当適性 × 係数（特性・状態で補正）。
4. **入手**: 日数経過で**ランダムユニット**（避難者）や**ユニークユニット**が加わる。
5. **喪失**: 飢餓で**死亡**、低士気で**離脱**。
6. **負傷・成長**: 医療不足で負傷（効果半減）、働くほど適性が成長。
7. **食料圧**: **ユニットは1人あたり食料を消費**する。戦力増と飯の負担のトレードオフ。

---

## 3. ユニットモデル

```ts
type Aptitude = 'labor' | 'tech' | 'medical' | 'charm'
type TraitId = 'hard_worker' | 'leader' | 'sturdy' | 'popular' | 'frail' | 'troublemaker' | 'clumsy'
type Condition = 'healthy' | 'injured'

interface Unit {
  id: string
  name: string          // 名前プールから。ユニークは固定
  portrait: string      // アートスロット portrait/{id}.png の id
  apt: Record<Aptitude, number>  // 各 1..10
  traits: TraitId[]     // 0..2
  condition: Condition
  xp: number            // 成長用
}
```

- **適性**: `labor`(道路) / `tech`(発電) / `medical`(医療) / `charm`(炊き出し)。配置先任務の対応適性で効果が出る。
- **特性**: 効果を乗算/加算する個性（§11）。
- **状態**: `injured` は効果半減。
- **成長**: 任務で働き適性を使うと、その適性が伸びる（§10）。

---

## 4. 配置の操作

**選択 → 配置**を基本に、ドラッグ・キーボード・おまかせを併設する。

| 操作 | 動作 |
| --- | --- |
| ユニット選択 → 任務クリック | その任務に配置 |
| 配置済みユニットをクリック | ロスターへ戻す |
| ドラッグ&ドロップ | 既存の `useTokenDnD` を流用 |
| キーボード | ユニット focus → Enter で選択、任務へ移動 → Enter で配置 |
| **おまかせ配置** | 貪欲法で全ユニットを最適配置（§4.1） |
| **リセット** | 全配置を解除しロスターへ戻す（再考を容易に） |
| **確認ステップ** | 未配置ユニットがいる状態で開始 → 「このまま開始 / 戻って調整」 |

- 思考中の配置は**その日限りのローカル状態**（日が変わるとリセット）。
- 「人員を選んで配置して…」の二段が、ユニットを直接置く一段になる。

### 4.1 おまかせ配置（貪欲法）

1. ユニットを「最大適性の高い順」にソート。
2. 各ユニットを、**自身の貢献が最大になる任務**へ割り当て（既配置分も加味して限界貢献で判定）。
3. 予算/備蓄のコスト制約（§5）を満たさない任務は候補から除く。

最適解の保証はないが、実用的な初期配置をワンタップで提供する。微調整は手動で。

### 4.2 ユニット能力の確認

配置の意思決定に必要な情報を、2層で出す。

**コンパクト表示（ユニットカード）** — 一覧で即読:

- 肖像 + 名前 + 状態（負傷マーク）
- **4適性のミニ表示**: 労/技/医/魅 を色つき数値または極小バーで並べる。色は任務と対応（労=amber / 技=cyan / 医=green / 魅=gold）で、ユニットの得意先が一目で分かる。
- 特性アイコン（詳細はモーダルで）
- ロスター（未配置）と任務スロット（配置済み）の**両方**に同じカードを出す。

**詳細モーダル** — カードのℹボタン / キーボード `i` で開く:

- 大肖像 + 名前 + 出自（フレーバー）
- 4適性バー（1〜10、数値つき）
- 特性: 名称 + 効果の説明文
- 状態: 健康 / 負傷（効果半減中）
- 成長: xp 進捗 +「どの任務でどの適性が伸びるか」

**配置操作との分離**:

- カード**本体クリック = 配置の選択**（§4 の操作）
- **ℹボタン / `i` キー = 詳細モーダル**（参照専用）
- 「動かす」と「見る」のジェスチャを分け、誤操作を防ぐ。

## 5. 任務効果（適性駆動）

各任務は対応適性を持つ。配置ユニットごとに貢献を計算し**合算**する。

```
ユニット貢献 = round((基礎 + 対応適性_実効 × 係数))
対応適性_実効 = 当該適性 + 指導者ボーナス(同任務の他ユニットにleaderがいれば +2)
乗算補正 = hard_worker ×1.3 / frail ×0.7 / injured ×0.5（重複は掛ける）
```

| 任務 | 対応適性 | 効果（初期値・要調整） | コスト |
| --- | --- | --- | --- |
| 発電所の修理 | tech | `電力 += Σ round(2 + tech × 1.8 × 補正)` | 予算 20 |
| 道路復旧 | labor | `食料 += Σ round(labor × 2.2 × 補正)` | — |
| 医療班増員 | medical | `医療 += Σ round(2 + medical × 1.5 × 補正)` | 予算 15 |
| 炊き出し | charm | `士気 += Σ round(3 + charm × 1.2 × 補正)` | 備蓄 15 |
| 配給を絞る | — | 消費×0.5 / 士気 −6（方針、ユニット不要） | — |

例: tech 8 の技術者を発電所に置くと `2 + 8×1.8 ≒ 16` 電力回復。複数置けば合算。

## 6. 経済（食料消費）

```
毎日の食料消費 = ユニット数 × perUnit(4)
```

- 初期4ユニット → 16/日。ユニットが増えるほど飯が重くなる。
- 道路復旧（食料搬入）との 균형で「ユニットを雇うか、飢えるか」の緊張が生まれる。
- 予算収入・電力ボーナス等の骨格は 09 を踏襲（数値は再調整）。

## 7. 入手

### 7.1 ランダムユニット（避難者）

- 既存の避難者イベント等が**ランダム生成ユニット**を1人追加。
- 生成: 名前プールから名前、適性は各 2〜6 の乱数（1属性だけ 5〜8 に尖る）、特性は 30% でランダム1つ。
- **v1 は自動加入**（§13）。加入翌日から食料を消費する（負担は暗黙のトレードオフ）。
- **上限**: ロスター最大 8。満杯なら加入せず「避難所にはもう余裕がない」。

### 7.2 ユニークユニット

固定の強いユニットが特定の条件/日数で加入（once イベント）:

| id | 名前 | 特徴 |
| --- | --- | --- |
| `stranded_engineer` | 取り残された技術者 | tech 9 / 頑丈 |
| `retired_medic` | 隠居した医師 | medical 9 / 指導者 |
| `young_volunteer` | 若いボランティア | labor 8 / 働き者・成長が早い |

---

## 8. 喪失

### 8.1 飢餓による死亡

- 日末で食料が尽きる（備蓄でも不足）と、**ロスターから完全にランダムな1ユニットが死亡**する（能力・貢献度は一切問わない）。
- `casualties++`、士気大幅低下、「誰が亡くなったか」を理由つきで報告。
- ランダムゆえに**育てたエースが急に死ぬ**こともある。「弱い個体を生贄に温存する」縮退戦略を封じ、誰も安全ではない緊張と愛着を生む。

### 8.2 離脱

- 日末で士気 < 20 のとき、ランダムなユニット1名が 30% で離脱（去る）。
- 戦力を失うが、残った者の士気はやや回復する。

---

## 9. 負傷

- 日末で医療 < 30 のとき、**その日働いたユニット**からランダムに負傷（基本25%、`clumsy` は2倍、`sturdy` は無効）。
- 負傷ユニットは任務効果が**半減**。
- 回復: 日末で医療 >= 50 なら負傷が治る（または日ごとに回復確率）。
- UI では負傷マークを表示。

---

## 10. 成長

- ユニットが任務で働くと `xp += 1`。
- `xp >= 5` で `xp -= 5`、**その任務の対応適性 +1**（上限10）。「修理で技術が伸びた」と報告。
- 使うほど適職が育ち、愛着と進行感が生まれる。`young_volunteer` は成長が早い（xp+2）等の差分も可。

---

## 11. 特性一覧

| id | 名称 | 効果 | 種別 |
| --- | --- | --- | --- |
| `hard_worker` | 働き者 | 任務効果 ×1.3 | 正面 |
| `leader` | 指導者 | 同任務の他ユニットの適性 +2 | 正面 |
| `sturdy` | 頑丈 | 負傷しない | 正面 |
| `popular` | 人気者 | 毎日 士気 +1（存在効果） | 正面 |
| `frail` | 虚弱 | 任務効果 ×0.7 | 負 |
| `troublemaker` | 問題児 | 毎日 士気 −1 | 負 |
| `clumsy` | 不器用 | 負傷確率2倍 | 負 |

特性は「効果の乗算/加算」と「日次の存在効果」の2種。ランダムユニットは 0〜1個、ユニークは固定で持つ。

## 12. 初期ロスター / 名前・肖像プール

### 12.1 初期4ユニット（旧「町長/医師/技術者」をユニット化 + 労働者1名）

| 名前 | labor | tech | medical | charm | 特性 |
| --- | --- | --- | --- | --- | --- |
| 嘉悦（町長） | 4 | 4 | 4 | 8 | 指導者 |
| 医師 | 3 | 5 | 9 | 5 | — |
| 技術者 | 5 | 9 | 3 | 3 | — |
| 農夫 | 8 | 3 | 4 | 4 | 頑丈 |

### 12.2 名前・肖像

- 名前はプール（例: 源吉/美代/宗助/ハル…）から抽選。肖像は既存の `portrait/{id}` アートスロットで、**未作成時は名前1文字のタイル**がフォールバック（既存のプレースホルダ機構）。
- ユニークは固定名・固定肖像 id。

---

## 13. イベント統合（自動 vs 選択）

- 現行のイベントは**自動解決**（06 §7、原子 day）。本設計も v1 はこれを踏襲し、**加入/喪失は自動**。
- 判断のつらさは「誰が死ぬか（飢餓）」「誰を配置するか（トリアージ）」「ユニット増と食料圧」から自然に生まれる。
- **将来拡張**: 「避難者を受け入れるか/追い返すか」等の**選択型イベント**（reducer に決定フェーズを追加）。v1 のスコープ外とし、設計だけ記録する。

## 14. 影響と移行

| 変更対象 | 内容 |
| --- | --- |
| `types.ts` | `Unit` 追加。`workers:number` と `characters:Character[]` を `units:Unit[]` に置換。`Assignment` → `Placement { task, unitIds[] }` |
| `actions.ts` | 効果計算を適性駆動に。`preview`/`resolvePlacement`。おまかせ配置の貪欲法 |
| `settlement.ts` | 食料消費 = units×4、負傷・死亡・離脱・成長・特性の存在効果を日末処理に追加 |
| `events-data.ts` | 避難者→ランダムユニット生成、ユニーク加入イベント、上限判定 |
| `balance.ts` | 新係数（適性係数・perUnit・成長閾値・負傷確率等） |
| UI | DecisionBoard をユニット配置に刷新（選択/ドラッグ/おまかせ/リセット/確認）、ユニットカード（4適性コンパクト表示 §4.2）+ 詳細モーダル、StatusWall から人員削除（ユニットは中央面板へ） |
| 決定性・simulation | ロジックは純粋のまま。random play を「ランダム配置」に更新し再チューニング |

アーキテクチャ（純粋reducer・データ駆動・アートスロット）は不変。差し替わるのはデータとロジックの内容。

---

## 15. バランスと simulation

- 目標は据え置き: **無作為（ランダム配置）で時々生存 / 熟練（適材適所）で安定勝利**。
- 実装後、simulation harness で勝率・ ending 分布・ユニット生存数を確認し、適性係数・食料単価・加入頻度を調整する。
- 確認観点: 初期4人で食料が回るか、ユニット増が「嬉しいが重い」か、飢餓/離脱/負傷が理不尽でないか。

---

## 16. 実装順序（案）

1. `types.ts` + 初期ロスター + ユニット生成（ランダム）
2. `actions.ts` 適性駆動の効果計算 + おまかせ配置
3. `settlement.ts` 食料消費・負傷・死亡・離脱・成長・特性効果
4. `events-data.ts` 加入/喪失イベント
5. UI 刷新（ユニットカード + 配置操作 + 詳細モーダル）
6. simulation 再チューニング
