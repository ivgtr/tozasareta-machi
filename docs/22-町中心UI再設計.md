## 1. 背景

現在のプレイ画面（docs/07 §3）は、StatusWall（状況）/ DecisionBoard（決定）/ ReportFeed+Skyline（記録+町の眺め）の三パネルを並べるダッシュボード構造。町の情景は右列の小窓にとどまり、プレイヤーが操作するのは町ではなくリストとカード。

Issue #1 の課題整理（情報パネルが主役 / 町が操作対象でない / 状況理解が文章寄り / 常時表示過多 / グラフィック要件が未定義）は現行実装と一致しており、採用する。

### 1.1 現行から持ち越すのは「実装」ではなく「語彙」

Phaser フル移行により React コンポーネント群は破棄されるが、そこで確立した**体験の語彙**は移植対象として維持する:

- トークンの DnD + タップ選択（配置の基本操作）
- 逐次プレイバック + スポットライト（結果を物語として見る）
- 低強調の確定操作（割当完了で初めて主張する）
- アートのフォールバック思想（画像未着時はグリフ表示で進行不能にしない）

## 2. 目的・非目標

Issue #1 の目的・非目標を採用する。要約:

- 画面の主役を情報パネルから町の情景へ移す（デスクトップで町領域 60〜75%）

## 3. 技術選定: Phaser フル移行（確定）

### 3.1 決定

ゲーム画面の全体（町シーン・HUD・詳細パネル・オーバーレイ・メニュー・タイトル）を **Phaser 3** で実装する。壁打ちでの比較（DOM拡張 / PixiJS / フルエンジン）を経て、**フルエンジンによる全面移行**を選択した。

選択の論点:

- 「情報画面にゲームの皮を被せる」のではなく「ゲーム画面を作る」という方針の振り切り。Phaser 側で画面全体を構成することで、React パネルと canvas の**継ぎ目がなくなり**、CRT・走査線・カメラ演出を全画面に一貫して適用できる
- ターン制の本作でも演出の要求は実時間的（トゥイーン・粒子・カメラフェード・フォーカス）。Phaser のシーン管理・トゥイーン・粒子・カメラ効果がそのまま使える
- 将来（カメラワーク・カットシーン・より高い生活感）への天井がない

### 3.2 アーキテクチャ

```text
src/game/       ゲームコア（不変。純粋 reducer・DOM非依存・lintで強制）
src/store/      zod スキーマ・セーブ・設定・履歴（React依存を剥がして純TS化。現 src/ui/store.ts から移植）
src/scene/      Phaser 実装（新設）
  scenes/       Boot / Title / Play / （必要なら Overlay 系は Play シーン内のレイヤーで持つ）
  town/         町空間データ（座標・施設配置・ヒット領域）/ 施設ビュー導出 / Effect→演出対応表
  ui/           Phaser 製 UIキット（PixelPanel/PixelButton/Gauge/TextButton の相当物）
  playback/     逐次再生の状態機械（現 usePlayback の純粋ロジック移植）
src/assets/     PNG アセット（現 src/ui/assets を移設。Phaser ローダーがビルド時URLマップで読む）
```

- **React は撤去する**。Vite エントリは Phaser の `Game` を直接マウントする
- **データの流れは一方向**: `GameState → シーンの表示`。Phaser シーンはゲーム状態を**持たない**（保持するのは表示キャッシュのみ）。入力は store 経由で `step` を呼ぶ
- プレイバック・選択フェーズ・セーブ/undo の**意味は現行と完全一致**させる（移植であり再設計ではない）
- Phaser のバージョンは **3**（文量・実績・AIエージェントの参照性）。`phaser-react-hooks` 等の接着ライブラリは不採用（React を撤去するため不要）

### 3.3 受け入れるコストと緩和策

| コスト | 内容 | 緩和策 |
| --- | --- | --- |
| 書き換え規模 | 現 React コンポーネント約19本が Phaser 実装に置換される v2 級作業 | §10 の並行構築+切替で、移行中もゲームを遊べる状態・CI緑を維持 |
| a11y の後退 | DOM が消え、スクリーンリーダーへのセマンティクス提供は実質失われる | **許容範囲を §11 に明文化**: キーボードフル操作・reduced-motion・aria-live 相当の DOM 告知ブリッジは作る。全画面の SR 対応は非目標化（§12 WB-11 で最終確認） |
| テスト戦略の変化 | 現 UI スモークテスト（React/jsdom）は破棄 | ゲームコア・決定性・sim のテストは**全件維持**。Phaser 側のロジックは純TS層（town/ui キットの判定関数）に分離して Vitest で測る。シーン描画はビルド+手動チェックリストで検証 |
| バンドル | Phaser 約1MB | ゲームとして許容。記録のみ |
| 日本語テキスト | Phaser Text は canvas 描画（日本語対応）。BitmapText は日本語グリフのアトラス化が高コスト | **DotGothic16 / Press Start 2P を Web フォントとして読み込み、Phaser Text で描画**する方針で固定。長文（ログ・イベント文）の描画コストは Phase 2 で実測 |

### 3.4 DOM フォールバック

Phaser は WebGL 初期化失敗時に Canvas レンダラへ自動フォールバックする（`type: AUTO`）。これを前提とし、WebGL 前提のコードを書かない。

## 4. 画面構成（Phaser シーン内）

### 4.1 デスクトップ

```text
+--------------------------------------------------------------+
| HUD: 日数 | 資源4 + 予算/備蓄 | 警報 | modifier/act | メニュー |
+--------------------------------------------------------------+
|                                                              |
|                町のメイン表示 (60-75%, アイソメ)              |
|         [発電]      [本部]                [診療所]            |
|   [倉庫]                  [広場]                             |
|                    [崩落地点・町の出口→]                      |
|     トークン（施設のタイル上に y-sort 表示）                   |
|     天候・灯り・状態演出（多層: 地面 / 施設 / fx / 空）        |
|     ※配置の正は docs/23 §1.3                                 |
+-------------------------------------------+------------------+
| 計画ストリップ: 割当一覧 / 予算残 / [自動割当] [確定]         | 人物トレイ
+-------------------------------------------+（待機トークン）
| 選択対象の詳細パネル（施設 or 人物。未選択時はヒント表示）      |
+--------------------------------------------------------------+
```

- HUD・計画ストリップ・詳細パネル・トレイは Phaser 製 UIキット（§3.2 `scene/ui/`）で構築
- 本部記録（ログ）は**折り畳みドロワー**。常時は最新2–3行
- CRT 走査線・ヴィネット・状態ティント（docs/07 §2.5）は全画面の最前面レイヤーとして再現
- オーバーレイ（選択イベント・加入/帰還スポットライト・エンディング・イベント再生）は Play シーン内の**前面レイヤー**として実装（別シーンにすると町の状態が途切れるため）

### 4.2 モバイル

町表示を上部に維持。人物トレイ + 詳細パネルは下部の**切替式パネル**（WB-9）。計画ストリップ + 確定は親指到達域に固定（現 CommitBar の思想）。寸法・スケーリングの詳細は §4.4–4.5。

### 4.3 計画ストリップ（必須要素）

施設選択モデルでは計画が1施設ずつの詳細パネルに分散するため、**全体計画の常設サマリー**が必須:

- 配置済み人員（任務別ミニトークン）、ration/procure のオンオフ、予算/人員の残
- `[自動割当]` `[確定]` の入口（autoAssign の維持）
- 低強調の思想を継承（割当完了で初めて主張する）

### 4.4 デバイスクラス・スケーリング方針

**レイアウトは2種のみ**（docs/07 の3区分から簡略化。Phaser ではレイアウト1種=実装コストのため）:

| クラス | 条件 | 設計サイズ（論理） | 用途 |
| --- | --- | --- | --- |
| **wide** | 幅 ≥ 900px | **1280×720** | PC・タブレット横持ち |
| **narrow** | 幅 < 900px | **480×854** | SP 縦持ち・タブレット縦持ち |

- SP は**縦横両対応**。縦=narrow、横=wide（圧縮）。クラスが変わったら Phaser の `scale.setGameSize` で設計サイズを切替 + リレイアウトする（resize/orientationchange の都度）
- クラス内は Scale Manager **FIT + CENTER_BOTH**。レターボックス色は `#0a0e24`（night-900。世界観の外側に出ない）
- Game 設定は `pixelArt: true` / `roundPixels: true`。町レイヤーは**可能な限り整数倍表示**を目標とする（ベース 480×320 は narrow で幅1倍・wide で約1.7倍）。非整数倍でのわずかなスケーリング artifacts は許容し、ゲートは「実機表示で滲み・ちらつきが見えないこと」
- narrow の設計幅 480 は docs/23 の町ベース幅と一致（1倍以上の表示を保証する）

### 4.5 領域配分と最小サイズ

**wide（1280×720）** — Issue の「町領域 60–75%」を満たす配分:

| 領域 | 寸法（論理px） | 備考 |
| --- | --- | --- |
| HUD（上帯） | 1280×48 | 日数・資源・予算/備蓄・警報・modifierバッジ・メニュー |
| 町領域 | 1280×460 | 画面の約64%。ベースは中央配置 |
| 計画ストリップ | 幅約840×48 | 町領域の下。autoAssign・確定 |
| 人物トレイ | 幅約440×48 | 計画ストリップと同行の右側 |
| 詳細パネル | 1280×164 | 底部。未選択時はヒント表示（常設） |
| ログドロワー | HUD から重畳 | 常時は最新2–3行 |

**narrow（480×854）**:

| 領域 | 寸法（論理px） | 備考 |
| --- | --- | --- |
| HUD（上帯） | 480×44 | CompactStatus 相当（日数+資源アイコン+警報） |
| 町領域 | 480×380 | ベース1倍+余白。 viewport 高さの約45%（SP の目標は「町が上部に支配的」であり、60–75% は PC 基準） |
| 計画ストリップ | 480×48 | 親指到達域に固定 |
| トレイ+詳細（切替式） | 480×220 | トレイは横スクロール。詳細は切替表示（WB-9） |
| ログドロワー | HUD から重畳 | — |

**最小サイズ・その他**:

| 項目 | wide | narrow |
| --- | --- | --- |
| タッチ/クリック対象 | ≥ 32×32 | **≥ 44×44**（視覚サイズが小さくてもヒット領域で確保） |
| 施設ヒット領域 | ≥ 64×48 | ≥ 64×48（ベース1倍時） |
| トークン表示 | 24×32 の1.5倍以上 | 同左 + ヒット領域 44×44 |
| 本文テキスト（DotGothic16） | ≥ 15px | ≥ 13px（実機 360px 幅で読めること） |
| ラベル | ≥ 12px | ≥ 11px |
| 日数カウンタ（Press Start 2P） | 28px | 20px |

- **セーフエリア**: ノッチ・ホームバーを避け、上下端 8px 以内には操作要素を置かない（`viewport-fit=cover` + safe-area-inset の読み取りは P2 で実装）
- ドラッグ操作は narrow でも維持（トークンの DnD。タップ二段階がフォールバック）

## 6. 施設モデル（アイソメ）

### 6.1 町空間

- **斜め見下ろし（2:1 ダイアモンド）**の論理グリッドを定義し、施設ごとの `{ gx, gy, anchor, footprint }` をデータ化（`src/scene/town/layout.ts`）
- ヒット判定は Phaser の Zone / ポリゴン入力。キーボード代替（施設リストの循環選択）は UIキット側で提供
- トークン・fx は施設のアンカーに配置し、**y-sort**（depth = 描画Y）で重なりを正しくする
- 多層構成: 地面ベース / 施設 / トークン / fx（煙・雨・浮遊表示）/ 空・天候 / 全画面フィルタ（CRT・ティント）

### 6.2 選択モデル

- 施設選択 → 詳細パネル（コスト・期待効果・配置済み人物・実行可否）。preview は `taskCost`/preview 関数を再利用
- トークン配置: トレイ→施設のドラッグ（Phaser drag）+ タップ二段階。配置可否は `sanitizePlan` 系の判定を再利用
- 探索中・負傷のトークンはトレイ側で状態表示（不在トークンは町に表示しない）
- **トークンの状態表現は画像を追加しない**: 負傷= Phaser の tint（赤系）+ バッジ記号、探索中=トレイ内の「探索中」バッジ（配置不可表示）。状態差分スプライトは作らない（docs/23 の制作点数に含めない）

## 7. 結果の町への反映

### 7.1 Effect→演出の対応表

Effect は `{ source, target, delta }` を持ち空間情報を知らない。対応表は **Phaser 側の写像**として集約する（`src/scene/town/fx-map.ts`）:

- `(source のパターン, target) → { 施設, 演出種 }`（例: `task:soup_kitchen × morale` → 広場・炊き出し煙 + 浮遊+表示）
- source は自由文字列のため、**対応表の網羅性を Vitest で保証する**（既知 source の列挙と突合）
- 未対応の effect は HUD 付近の汎用浮遊表示へフォールバック（グリフ思想の継承）
- **先行準備（docs/25 音響構想）**: 対応表は将来 `sfx` フィールドを追加できる形（写像テーブル経由の一括解決）で設計する。発火点は playback ビートに集約し、音導入時に機構を作り直さない

### 7.2 プレイバックの移植

- 現 `usePlayback` の**純粋ロジック**（ビート分解・進行・applyEffects 相当）を `src/scene/playback/` の状態機械へ移植。ビートモデル（flow/event/arrival）とスポットライトの意味は不変
- flow ビート: 対応表による施設演出（トゥイーン・浮遊表示・状態遷移）
- event ビート: 前面レイヤーのイベントパネル + 必要に応じカメラフォーカス（対象施設以外を減光）
- arrival ビート: トークンが町の入口（崩落地点/本部）に出現。スポットライトは維持

### 7.3 町の環境表現

- 電力水準 → 町の灯り（施設スプライトの発光レイヤー + 全体明度）
- 危険（morale < riotAt / food 0）→ ティント・パルス（AmbientBackdrop の思想を全画面フィルタで再現）
- 天候イベント → 雨層・雲（粒子 or steps() 相当のトゥイーン）
- **空のみアクト連動**（WB-6 確定）: 時間帯は**夜固定**（既存アセットと完全整合・追加制作ゼロ）。膠着期/正念場で空の色調・雲・星を Phaser の tint で微調整する（画像追加なし）

---

## 8. Modifier・アクト・脅威度の表現

1. **HUD バッジ**（情報の保証）: 発動中の modifier・現在アクト（膠着期/正念場）を常設表示。modifier の発動/解除は flow ビートのトーストで告知（docs/17 M3 残項目を吸収）
2. **町の環境連動**（演出、WB-8 確定）: 対象は**アクト遷移 + 視覚的に明確な一部 modifier**（cold_snap 等）のみ。全22件の連動は行わない。**バッジを正**とし、環境連動は「あれば良い」層に留める

## 9. アセット

### 9.1 アイソメのアセット契約（確定 → docs/23）

投影・寸法・パレット・レイアウト・生成プロンプトは **[docs/23-町アセット制作計画](./23-町アセット制作計画.md) に確定済み**。要約:

- **2:1 ダイアモンド投影**（タイル 48×24）。ベース 480×320 / 施設 96×112（接地 96×48）/ トークン 24×32。既存9色パレット・左上光源を維持
- 施設スプライトは**透明背景**でベースへ重ねる（従来の不透明アセットと扱いが異なる）。状態差分は同寸法 PNG の差し替え
- トークンIDは portrait ID と同一。ユニーク30体は汎用8種プールの決定的割り当てへフォールバック（docs/14 §4 の流儀）
- 選択強調・配置可否は画像差分にせず、Phaser のグラフィックス/トゥイーンで描画（Issue 方針の維持）

### 9.2 命名と kind

```text
facility/{施設id}-{状態}.png   例: facility/power-normal.png / power-working.png
town/base.png                  地面ベース
token/{unit-id}.png
fx/{演出id}.png                必要になったものから（粒子で代替可）
```

状態接尾辞の基本セットは `normal / damaged / working / restored / selected` とするが、**施設ごとの最終確定は docs/23 §1.2**（power=normal/low/working、road=collapsed/working/restored 等）。manifest（グリフ・色・ラベル）は `src/scene/art/` 相当として再構築し、**フォールバック（画像未着→グリフ描画）を維持**。アセット検出はビルド時の URL マップ（`import.meta.glob`）で Phaser ローダーへ渡す。

### 9.3 既存アセットの扱い

| アセット | 扱い |
| --- | --- |
| skyline 3バリアント | アイソメ町ベース採用により**役割終了**。空・遠景の参考としてのみ保持 |
| portrait（ユニーク30+汎用8） | 詳細パネル・トレイの顔表示として**再利用**（Phaser image。新規制作不要） |
| icon 群 | HUD・計画ストリップで再利用 |
| event PNG（20件+プレースホルダ22件） | Issue §F 方針どおり低優先。イベントパネル内で継続利用 |
| ending 4枚 | エンディング画面で維持 |

### 9.4 制作規則

Issue の「AI画像生成の運用方針」を採用: 共通プロンプト（視点=アイソメ・光源・パレット・輪郭・陰影・透過・サイズ・禁止事項）を固定し、変動部は対象と状態のみ。ゲート（縮尺・光源方向・輪郭線太さ・小サイズ識別性・**差分間の形状一致**・投影角度の一致）は docs/14 §3.2・docs/15 の延長で定義。アイソメは角度の機械的検証が難しいため、**ゲートに基準施設との並べ置き目視比較を必須**とする。
