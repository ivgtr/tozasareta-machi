# 参考プロジェクト研究: VimnaganoYabo

[戦国風雲録 〜Vimで天下統一〜](https://github.com/miraihack/VimnaganoYabo)（以下、本プロジェクト）は、信長の野望風の戦国SLGを **外部依存なし・単一ファイル（Vim script 約2400行）** で実現したもの。コードを写すのではなく、**実装の考え方**と**ゲーム制作の考え方**を抽出し、本作「孤立した町の30日間」へどう持ち込むかをまとめる。

---

## 1. 実装の考え方（アーキテクチャ）

### 1.1 ビルド環境は最初から整備する（単一ファイルは真似しない）

本体は `plugin/sengoku.vim` の1ファイル・外部依存ゼロ。ただしこれは **Vim plugin という配布形態に由来する制約**であり、ブラウザゲームに持ち込むべき教訓ではない。ビルド工程を後から導入すると、モジュール分割・型検査・テストランナーの接続すべてが負債として跳ね返る。

**考え方**: ブラウザゲームではビルド環境（Vite + TypeScript など）を最初に敷く。この投資は、後述する「ゲームコアの分離」や「ヘッドレスな自動テスト」（3章）を cleanly 実現するための土台になる。本プロジェクトから移植すべきは「ビルドを避ける」ことではなく、**ゲームの中身をUIから切り離して単体で動かせる形にする**という発想。

**本作への適用**:
- 最初に Vite + TypeScript でプロジェクトを立ち上げる。
- ゲームコア（状態定義・ルール・イベント解決・ターン進行）を、DOM に依存しない純粋なモジュール（`src/game/` 等）として実装する。描画と入力は別の層（`src/ui/`）に置く。
- この分離により、ゲームコアはブラウザ上でもテストランナー（Vitest など）上でも同じコードが動く。単一ファイルのままでは得られない恩恵。

### 1.2 データとロジックを分離する（データ駆動）

大名家・国・武将・茶器などのコンテンツは、それぞれ「データを返す関数」（`Clans()` / `ProvDefs()` / `GenDefs()` / `Items()`）として定義され、ゲームロジックから切り離されている。国データは `[名前, 大名家, 行, 列, 隣接, 石高, 商業, 兵, 特記]` のような単純なテーブル。

**考え方**: バランス調整やコンテンツ追加が「データ表の編集」だけで済み、ロジックに手を入れなくてよい。イベント20種・エンディング3種を持つ本作と相性が良い。

**本作への適用**: イベントは「条件 / 発生確率への補正 / 効果 / 表示文」を持つデータテーブルとして定義する。イベント追加 = 行追加、になる形を目指す。

### 1.3 状態は一箇所に集約し、シリアライズ可能にする

ゲーム状態は `s:prov`（国）`s:clans`（家）`s:gens`（武将）`s:ally`（同盟）などの集約変数にまとめ、`InitState()` 一つで初期化される。セーブ/ロードはこの状態をまるごと JSON に吐くだけ（`Save()` / `Load()`）。

**考え方**: 状態の所在が散らばると、セーブ・テスト・デバッグがすべて難しくなる。「全状態を1つのオブジェクトで表せる」設計にすると、巻き戻し・再現・自動テストが容易になる。

**本作への適用**: 町の状態（食料/電力/医療/士気、作業員、予算、備蓄、経過日数、フラグ類）を1つの game state オブジェクトに集約する。これにより「N日目の状態」を丸ごと保存・復元できるようになる。

### 1.4 参照は名前ではなくID（index）で持つ

国の隣接は最初は名前で持ち、初期化時に index へ解決する（`p.adj = map(...PIdx...)`）。同盟は「小さいindex-大きいindex」という正規化キーで管理し、重複や取りこぼしを防ぐ。

**考え方**: 文字列参照はタイポ・リネームに弱く、整合性チェックも難しい。ID化すると「隣接の対称性」「所有の一意性」を機械的に検証できる（後述のセルフテストに直結）。

### 1.5 ターンを「段階の並び」として設計する

ゲームループは明示的なパイプライン。

```
GameLoop:
  PlayerTurn()   → プレイヤーの入力
  AITurns()      → AIの行動
  CheckEnd()     → 勝敗判定
  MonthEnd()     → 月末処理（収入・消費・収穫・災害・一揆・イベント）
  CheckEnd()     → 勝敗判定
```

**考え方**: 「入力 → 解決 → 清算」を分離すると、各段階を独立して理解・テスト・修正できる。特に**清算フェーズ（MonthEnd）を入力の後で一括実行する**のがポイント。プレイヤーが行動した直後ではなく、1日の終わりに世界が動く。

**本作への適用**: 1日 = `プレイヤーが行動を選ぶ → 行動を解決する → 1日の終わりに資源増減・イベント判定・状態変化を一括適用 → 結果を報告`。この順番を守ることで「自分の選んだ行動が、翌日の状態をどう変えたか」が追跡しやすくなる。

## 2. ゲーム制作の考え方（メカニクス）

### 2.1 資源ではなく「行動回数」を制約にする

本プロジェクトの巧みな設計: **武将数 = その月の行動力**。各コマンドは武将を1人消費し、動ける武将が尽きたらその月は追加の仕事ができない（`UnusedGens` / `gused`）。

**考え方**: 「金がないと何もできない」は単調だが、「できることの総量に上限がある」は取捨選択を生む。制約を資源そのものではなく**行動の回数**に置くと、プレイヤーは常に「どれを切るか」を迫られる。

**本作への適用**: 設計ドキュメントの「作業員」を、まさにこの行動力として扱う。作業員の数 = 1日に実行できる行動の数。食料や予算は行動の「コスト」、作業員は行動の「枠」として役割を分けると、交換条件が明確になる。

### 2.2 「誰に任せるか」で結果が変わる（数値が意味を持つ）

同じ「開発」でも担当武将の政才で効果が変化（`p.koku += 12 + gen.pol/8`）。出陣は大将の戦才が全軍に影響。つまり資源配分だけでなく**人員配置**が判断になる。

**考え方**: 数値（能力値）は、それ自体が面白さではなく「選択に重みを与える装置」。数値が違うと同じ行動の結果も変わり、プレイヤーは「この貴重な1手を誰に託すか」で悩む。

**本作への適用**: 登場人物（町長・医師・技術者など数人）に得手不得手を持たせ、「発電所の修理に技術者を割くか、医療班に回すか」という人員配置の悩みを作る。設計原則「正解を一つにしない」を、人員制約で自然に実現できる。

### 2.3 状態が閾値を越えるとイベントになる

イベントは純粋ランダムではなく、状態に依存する。

- `loyal < 25` かつ 30% で一揆勃発
- `rice < 0`（兵糧切れ）で兵が逃散し民忠も低下
- 8〜9月に 12% で台風

**考え方**: 「過去の判断が発生源を変える」を、**状態変数の閾値 × 確率**という単純な式で実現している。複雑なイベントスクリプト言語は不要。

**本作への適用**: 「士気が低い状態が続けば抗議」「医療を放置すれば感染症」は、`士気 < X で抗議確率+` `医療 < Y で感染症確率+` という閾値ルールで実装できる。イベントデータに「発動条件（状態の閾値）」と「確率補正」を持たせればよい（1.2 のデータ駆動と組み合わせる）。

### 2.4 AIも同じ制約で動かす（公平さ）

AI大名もプレイヤーと同じ「武将1人=1行動」の制約で動く（`AIProvAct`）。行動は単純な優先度順（勝てそうな敵に進攻 → 交易 → 内政）。最適ではないが、同じ土俵なのでプレイヤーは「自分だけ不利」と感じにくい。

**考え方**: AIを賢くするより、**同じルールの中でそれらしく振る舞わせる**方が、設計の一貫性を保ちつつ低コスト。本作では「30日間の世界」が相手なので対戦AIは不要だが、「住民の反応」「避難者の流入」などの世界側ロジックも、プレイヤーと同じ資源制約の下で動かすと説得力が出る。

### 2.5 結果には必ず「理由」を添えてログする

`MonthEnd` の各処理は、状態変化と同時にログを残す。

- `兵糧が尽きN人が逃散……`
- `一揆勃発! 兵-N 石高減`
- `豊作! 米+N` / `凶作……`

**考え方**: 設計原則「プレイヤーに結果の理由を伝える」を、**変化を起こした処理の 바로隣でログを出す**ことで実現している。後から理由を再構成するのは難しいので、原因と結果が同じ場所にあるうちに記録する。

**本作への適用**: 資源を増減させる処理ごとに「なぜその変化が起きたか」の1文をセットで生成する（「食料配給を3日減らしたため、住民の不満が高まった」）。

## 3. 開発の進め方（テスト・検証）

### 3.1 組み込みのセルフテストを持つ

`:SengokuTest`（`SelfTest`）は、人間が遊ばずにゲームの健全性を検証する。

1. **マップ整合性**（`ValidateMap`）: 隣接の対称性・グリッド衝突・名前解決の不備を検出
2. **データ検証**: 各家の武将数、能力値の範囲（0超〜100以下）
3. **全自动シミュレーション**: プレイヤー不在で AI 31家 × 36ヶ月を回す
4. **不変条件（invariant）の表明**: 資源に負の値がない、茶器の所有が重複しない、同盟キーが正規化されている、勝敗と領有変化が一致する
5. **描画検証**: 画面が空でないこと、ポップアップが出ていること

**考え方**: バランス崩壊や状態破壊（資源がマイナスになる等）は、人が遊ぶより**AIに大量に回してもらう**方が早く見つかる。「回して壊れないか」を自動で確認する手段を、ゲーム本体と同時に作る。

**本作への適用**:
- **状態の不変条件を定義する**: 各資源は 0〜上限の範囲、経過日数は 0〜30、作業員数は非負、など。
- **ヘッドレスシミュレーション**: UI なしで「ランダムに行動を選ぶ」自動プレイを N 日分回し、不変条件が破られないか確認する。イベント確率や平衡（30日持ちこたえられるか/簡単すぎないか）の体感もここで掴む。
- ブラウザなら、ゲームロジックを UI から分離しておくと（1.3 の状態集約が前提）、コンソールやテストランナーから直接回せる。

### 3.2 データの誤りは機械に検出させる

隣接テーブルのような手書きデータは、人間の目では非対称や衝突を見落としやすい。`ValidateMap` のように「A→B があるなら B→A もある」「同じ座標に2国ない」をコードで検査すると、コンテンツ追加時の事故を防げる。

**本作への適用**: イベントデータ（存在しない資源を参照していないか、条件式が妥当か）や、状態遷移（ある行動が到達不能な状態を作らないか）を検査するバリデータを早期に用意する。

### 3.3 中断に強くする（オートセーブ）

`Ctrl-C` での中断を例外で捕捉し、即座に自動セーブする。状態が1箇所に集約されている（1.3）からこそ、いつでも安全に中断・再開できる。

**本作への適用**: ブラウザなら localStorage への状態保存が容易。30ターンは短いとはいえ、いつでも再開できるとプレイの心理的負担が下がる。

## 4. 本作に持ち込む要点（チェックリスト）

実装を始める前に、以下の方針を設計に反映できているか確認する。

- [ ] ビルド環境（Vite + TypeScript など）を最初に整備する
- [ ] ゲームコア（状態・ルール・解決）をDOM非依存のモジュールにし、UI層と分離する
- [ ] ゲーム状態を1つのオブジェクトに集約し、JSON で保存/復元できる
- [ ] イベント・エンディングはロジックと分離したデータテーブル
- [ ] 1日を「入力 → 解決 → 一括清算 → 報告」のパイプラインで設計
- [ ] 制約の中心は資源ではなく**行動回数（作業員）**
- [ ] 登場人物の得手不得手で「誰を割くか」の悩みを作る
- [ ] イベントは「状態の閾値 × 確率」で発火（過去判断に依存）
- [ ] 状態変化の処理の隣で「理由つきのログ」を生成
- [ ] 不変条件（資源範囲・日数範囲）を定義し、自動プレイで検証
- [ ] データの整合性バリデータを用意
- [ ] 状態集約を前提に、いつでもセーブ/再開できる
