# 技術設計書: 孤立した町の30日間

要件書（01〜04）と参考プロジェクト研究（05）を踏まえ、実装に進める粒度まで落とし込んだ技術設計。

---

## 1. 方針と確定事項

壁打ちで確定した判断。これらは本設計の前提であり、実装で揺らさない。

| 項目 | 決定 |
| --- | --- |
| 実行環境 | ブラウザ。Vite + TypeScript |
| UI層 | React（ゲームコアはDOM非依存のまま） |
| 中心抽象 | 純粋な reducer。`step(state, action) => { state, effects }` |
| 状態更新 | 不変（毎回新しい state を返す）。undo を初版から |
| undo | 日単位。history は **State の外側**（store層）に保持 |
| 乱数 | シード付き RNG を **State の内側**に保持。`Math.random` 不使用 |
| 1日の操作 | 作業員割り当てを UI で組み立て、`commitDay(plan)` で原子提交 |
| イベント(v1) | 自動解決＋理由報告。プレイヤー選択は挟まない |
| イベント発火 | 条件通過候補から重み付きで1日1件抽選 |
| 資源モデル | 食料=在庫 / 電力・医療=容量(0-100) / 士気=指標(0-100) |
| day pipeline | `commitDay → 行動解決 → 日次清算 → イベント → 日付進行・終了判定 → レポート` |

## 3. 状態モデル

### 3.1 GameState

```ts
export interface GameState {
  version: number;            // セーブフォーマット版
  day: number;                // 現在計画対象の日。1..30
  phase: 'planning' | 'ended';
  resources: Resources;
  workers: number;            // 1日に割ける作業員の総数
  budget: number;             // 予算
  stockpile: number;          // 備蓄品
  characters: Character[];
  flags: Flags;               // 累積状態（イベント条件・エンディングに使用）
  rng: RngState;              // 乱数状態（State の内側）
  report: Effect[];           // 直近1日に起きた効果（描画・ログ用）
  ending?: Ending;            // phase === 'ended' のとき設定
}
```

`report` は State の内側（フラットで直近1日分のみ）。**history は State の外側**（4章）。スナップショットが自己参照して肥大化するのを防ぐ。

### 3.2 資源

```ts
export interface Resources {
  food: number;      // 在庫。日次で消費。下限なしの計算後 clamp
  power: number;     // 容量 0..100（発電・送電の整備水準）
  medical: number;   // 容量 0..100（医療体制）
  morale: number;    // 指標 0..100（住民の士気）
}
```

意味の違いが清算式と悩みの質を決める（詳細は6章）。

- **food（在庫）**: 温存か放出かの「今日か明日か」を体現する資源。
- **power / medical（容量）**: インフラの整備水準。自然減衰・故障で下がり、行動で回復する。他の行動や結末を有効化/抑制する。
- **morale（指標）**: 他資源の状態を受けて漂移する結果指標。閾値で結末（抗議・暴動）を引き起こす。

### 3.3 人物・フラグ・乱数

```ts
export interface Character {
  id: string;
  name: string;       // 町長 / 医師 / 技術者 など
  role: string;
  skill: number;      // 担当行動の効果に影響（得意不得意）
}

export interface Flags {
  daysWithoutMedical: number;  // 医療が低水準で放置された連続日数
  daysFoodCut: number;         // 配給を絞った連続日数
  casualties: number;          // 累積犠牲者（エンディング判定用）
  refugeesAccepted: number;    // 避難者受け入れ回数
  cooperation: number;         // 住民協力の醸成度（住民自治END用）
  fired: string[];             // 発火済みの once イベント id
}

export interface RngState {
  seed: number;
  counter: number;   // 呼び出し回数。再構成・再現に使用
}
```

## 4. Action / Effect / store

### 4.1 Action と DayPlan

ゲームプレイ上の Action は `commitDay` のみ。undo は reducer へ渡さず store 層で処理する。

```ts
export type TaskId =
  | 'repair_power'       // 発電設備の修理
  | 'restore_road'       // 道路復旧（食料確保）
  | 'reinforce_medical'  // 医療班の増員
  | 'soup_kitchen'       // 炊き出し（士気回復）
  | 'ration';            // 配給を絞る（食料温存、士気減）
// 待機は任務にしない。未割当 = 待機（09 §5 で確定）

export interface Assignment {
  task: TaskId;
  workers: number;        // 割く作業員数
  characterId?: string;   // 担当人物。skill が効果に影響
}

export interface DayPlan {
  assignments: Assignment[];
}

export type Action =
  | { type: 'commitDay'; plan: DayPlan };
```

制約: `sum(assignments.workers) <= state.workers`。違反は UI 側で防ぐが、reducer 側でも clamp し不変条件を保つ。

### 4.2 Effect（理由つきの構造化ログ）

差分から文章を逆算せず、各ルールが Effect を生成する。UI はこれを文章化し、テストはこれを表明する。

```ts
export interface Effect {
  day: number;          // 発生した日
  source: string;       // 'task:repair_power' / 'settlement' / 'event:refugees'
  target: EffectTarget; // 'food' | 'power' | 'medical' | 'morale' | 'workers' | 'budget' | 'stockpile' | 'flag:xxx'
  delta: number;
  reason: string;       // 「発電設備を修理したため、電力が回復した」
}
```

### 4.3 store層（State の外側）

```ts
export interface StoreState {
  state: GameState;       // 現在の世界
  history: GameState[];   // undo 用スナップショット（各 commitDay 直前）
}
```

- `dispatch(commitDay)`: 現在 state を history に push → `step` を呼ぶ → 新 state で置き換え → 自動セーブ。
- `undo()`: history を pop し current に戻す。report も state 内なので同時に戻る。
- 永続化（5章）は StoreState を対象とする。

## 5. step の契約と day pipeline

### 5.1 契約

```ts
export interface StepResult {
  state: GameState;
  effects: Effect[];   // = result.state.report と同一
}

export function step(state: GameState, action: Action): StepResult;
```

- **純粋**: 同一入力（state + action）に対して同一出力。DOM・`Math.random`・現在時刻・外部可変状態に触れない。
- **不変**: 入力 state を破壊しない。新しい state を返す。
- **乱数は state 経由**: 内部の RNG 消費は `state.rng` を更新する形で表現。出力 state に次 RNG 状態を含む。
- React StrictMode は reducer を二重実行するが、純粋であれば結果が一致し進行が分裂しない。この性質は決定性テスト（8章）で検証する。

### 5.2 pipeline（commitDay）

```
step(state, { type:'commitDay', plan }):
  1. resolveActions(state, plan)   # 各 Assignment を TaskDef.resolve で解決
  2. settlement(state)             # 消費・減衰・漂移・閾値結末
  3. events(state)                 # 条件通過候補から重み付き1件抽選・適用
  4. advance(state)                # flags 更新, day++, 終了判定 → ending
  5. report を state.report に格納し、{ state, effects } を返す
```

順序の意図: プレイヤーの行動はその日の「対応」なので先に解決し、その日のコストと偶然（清算・イベント）が後から世界に効く。この順序はバランスに影響するため、定数として管理しチューニング対象とする。

## 6. 資源の清算モデル

初期値はすべて **要チューニング**。`src/game/data/balance.ts` に集約し、ロジックから分離する。

### 6.1 食料（在庫）

```
consume = BASE_FOOD_CONSUME            # 人口相当の固定消費（単純化）
food -= consume
food < 0 のとき:
  shortfall = -food
  food = 0
  casualties += shortfall 相当
  morale -= STARVATION_MORALE_PENALTY
  reason: 「食料が尽き、犠牲が出た」
```

行動 `ration`（配給を絞る）は consume を下げるが morale を下げ `flags.daysFoodCut++`。「今日を生きるか明日に温存するか」の中核。

### 6.2 電力・医療（容量）

```
power -= POWER_DECAY                   # 自然減衰
  + 低確率で故障イベント（events 側）で大減
repair_power: power += f(workers, 担当の skill)

medical -= MEDICAL_DECAY
reinforce_medical: medical += f(workers, skill)

medical < MEDICAL_LOW を継続:
  flags.daysWithoutMedical++           # 感染症イベントの重みを上げる
  回復するとリセット
```

容量は「他を有効化する」役割を持つ。例: power が低いと医療行動の効率が落ちる、など相互依存を1つだけ入れると交換条件が深くなる（入れすぎない）。

### 6.3 士気（指標）

```
morale += BASE_DRIFT
food 不足時:        morale -= X
daysFoodCut > 0:    morale -= Y        # 配給抑制の不満
medical 低水準:     morale -= Z
soup_kitchen:       morale += f(workers, skill)
clamp(0, 100)
```

### 6.4 閾値結末（settlement が担当、イベントではない）

```
morale < RIOT_THRESHOLD:
  workers または budget を損失
  reason: 「住民の不満が爆発し、作業が滞った」
```

閾値結末は「状態が必然的に招く結果」、イベントは「偶然の出来事」と役割を分ける。これによりレポートの因果が明確になる。

### 6.5 状態ラベル（数字を見せない）

要件書03の方針。純粋関数として実装し UI が使う。

```ts
export function moraleLabel(m: number): string {
  if (m >= 80) return '住民は協力的';
  if (m >= 40) return '不安が広がっている';
  if (m >= 20) return '不満が表面化している';
  return '暴動の危険がある';
}
```

## 7. イベントDSL

### 7.1 定義

イベントはコード（TS オブジェクト、関数つき）。シリアライズが必要なのはセーブデータであり、イベント定義はコード側なので DSL を JSON 化する必要はない。

```ts
export interface EvalContext {
  state: GameState;      // read-only
  flags: Flags;
  day: number;
}

export interface ApplyContext extends EvalContext {
  rng: RngState;         # 適用内の乱数（効果の揺らぎ用）
}

export interface EventDef {
  id: string;
  name: string;
  once?: boolean;                              # 一度きり
  when: (ctx: EvalContext) => boolean;         # 発動条件
  weight: (ctx: EvalContext) => number;        # 重み（0 は抽選から除外）
  apply: (ctx: ApplyContext) => Effect[];
}
```

### 7.2 発火エンジン（1日1件）

```
candidates = EVENTS.filter(e =>
  (!e.once || !flags.fired.includes(e.id)) &&
  e.when(ctx) &&
  e.weight(ctx) > 0)

candidates が空 → イベントなし
重み付き乱数で1件選出（rng を消費）
effects = chosen.apply(ctx)
once なら flags.fired に追加
```

### 7.3 例（過去判断で確率が変わる）

```ts
const infection: EventDef = {
  id: 'infection',
  name: '感染症の発生',
  when: ({ state }) => state.resources.medical < 30,
  // 医療が低いほど、放置が長いほど重くなる
  weight: ({ state, flags }) =>
    (30 - state.resources.medical) / 30 * 2 + flags.daysWithoutMedical * 0.5,
  apply: ({ state }) => [
    { day: state.day, source: 'event:infection', target: 'medical', delta: -15,
      reason: '医療を放置したため感染症が広がり、医療体制が逼迫した' },
    { day: state.day, source: 'event:infection', target: 'morale', delta: -10,
      reason: '感染症への不安で士気が下がった' },
  ],
};

const refugees: EventDef = {
  id: 'refugees',
  name: '隣町からの避難者',
  when: ({ day }) => day >= 5,
  weight: ({ flags }) => flags.refugeesAccepted === 0 ? 1 : 0.3,
  apply: ({ state }) => [
    { day: state.day, source: 'event:refugees', target: 'food', delta: -40,
      reason: '避難者を受け入れ、食料を分け合った' },
    { day: state.day, source: 'event:refugees', target: 'flag:cooperation', delta: 1,
      reason: '助け合いの空気が生まれた' },
  ],
};
```

`weight` が `flags`（過去の判断の蓄積）を参照することで、要件書の「過去の判断で発生確率が変わる」を実現する。

## 8. 終了条件とエンディング

```ts
export type Ending =
  | 'full_recovery'      // 完全復旧
  | 'managed_sacrifice'  // 管理された犠牲
  | 'self_governance'    // 住民自治
  | 'collapse';          // 崩壊（失敗）
```

### 8.1 早期終了（失敗）

`advance` 内で判定。`morale <= 0` または `casualties >= COLLAPSE_THRESHOLD` で `ending = 'collapse'`、`phase = 'ended'`。

### 8.2 30日目到達時の評価

```ts
export function evaluate(state: GameState): Ending {
  const { resources, flags } = state;
  const infraOk = resources.power >= 60 && resources.medical >= 60;
  if (flags.casualties >= SACRIFICE_THRESHOLD) return 'managed_sacrifice';
  if (flags.cooperation >= COOP_THRESHOLD && !infraOk) return 'self_governance';
  if (infraOk && flags.casualties < SACRIFICE_THRESHOLD) return 'full_recovery';
  return 'managed_sacrifice';   // 既定
}
```

分岐の優先順位と閾値は要チューニング。同じクリアでも方針で結果が変わることを保証する（要件書02）。

## 9. 乱数（rng）

```ts
// mulberry32 等のシード付き PRNG を純粋関数で包む
export function nextRandom(rng: RngState): [number, RngState] {
  // [0,1) の値と、更新済み rng を返す。外部状態を変えない
}
```

- reducer は `nextRandom` を使い、必ず返ってきた新 rng を state に書き戻す。
- **同一 seed + 同一行動列 ⇒ 同一 state** が成り立つ。これが再現・リプレイ・決定性テストの根拠。

## 10. undo と永続化

### 10.1 undo

- store は `commitDay` のたびに直前 state を `history` に push。
- `undo()` = pop して current に復元。State が不変なのでスナップショットは安全に共有できる。
- 上限（例: 直近30件 = 全日数）を設ける。
- 代替手段として、seed + 行動ログからのリプレイも可能（純粋性の副産物）。デバッグ用途。

### 10.2 セーブ / ロード

```ts
interface SaveData {
  version: number;        // GameState.version と一致するか検査
  store: StoreState;      // state + history
}
```

- localStorage に JSON で保存。`commitDay` ごとに自動セーブ（要件: 中断に強く）。
- ロード時は `version` を検査し、不一致なら migrate または拒否（参考PJの「旧版のデータです」対応）。
- State がシリアライズ可能（関数を含まない）であることが前提。イベント定義はコードなので保存対象外。

## 11. React 連携

- `store.ts` を `useReducer` または小規模ストアでラップ。`StoreState` を購読。
- dispatch は `{ type: 'commitDay', plan }` のみ。undo は store のメソッド。
- 描画は state の全量から再構成（ターン制で更新が疎なので最適化は不要）。

主要コンポーネント:

| ReportView | `state.report` の Effect を理由つきで列挙 |

## 12. テスト戦略

ゲームコアは DOM 非依存・純粋なので、Vitest で直接テストする。

### 12.1 単体

- 各 `TaskDef.resolve`:  crafted state + assignment → 期待 Effect。
- `settlement`: 食料切れ・士気閾値などの結末。
- 各 `EventDef.when / weight / apply`: 条件と効果。

### 12.2 決定性（最重要）

```
同一 seed + 同一行動列で step を2系統実行 → 最終 state が deep equal
```

RNG の漏れや非純粋（StrictMode での分裂）を捕捉する。

### 12.3 シミュレーション / 不変条件

seed を変えて N 回のフル自動プレイ（ランダム plan）を実行し、以下を表明。

- 全資源が定義域内（NaN / 負の不正値なし。food は 0 以上 clamp 済み）
- `day` が 30 に到達するか、`collapse` で早期終了する
- 終了時に `ending` がちょうど1つ設定される
- `casualties >= 0`、`flags.fired` に重複なし

参考プロジェクトのセルフテスト（AI に大量に回して健全性を検証）に相当。バランスの体感（簡単すぎ/厳しすぎ）もここで掴む。
