# 設計原則

設計判断に迷ったときの基準。新要素の追加可否もこれらで判断する。

## 「何を管理するゲームか」より「何に悩むゲームか」

シミュレーションゲームでは、管理項目を増やすだけでは面白くならない。プレイヤーに悩ませたい核心は次の一文。

> 今日を生き延びるために備蓄を使うか、明日のために温存するか。

新しい要素を追加するときも、この悩みを深くするものは残し、単に操作量を増やすだけのものは削る。

## 正解を一つにしない

発電所を直すことが常に正解なら、プレイヤーは考えなくなる。

- 電力を優先して復旧を早める
- 医療を優先して死者を減らす
- 士気を優先して住民の協力を得る

どれも成立するようにする。ただし、何を選んでも同じ結果になるのも避ける。選択によって得意な状況と苦手な状況が変わる形が理想。

## プレイヤーに結果の理由を伝える

結果が悪かったときに「運が悪かった」としか思えないゲームは改善しづらい。

単に「士気が10下がった」と表示するより、次のように示す。

> 食料配給を3日間減らしたため、住民の不満が高まった。

こうすることで次のプレイに知識を持ち越せる。シミュレーションゲームにおける上達とは、操作が速くなることではなく、**世界の仕組みを理解すること**。

## 数字より状態を見せる

すべてを数値で表示すると、表計算ソフトのように見える。数値に加えて、状態を言葉で表す。

| 数値 | 表現例 |
| --- | --- |
| 士気80以上 | 住民は協力的 |
| 士気40〜79 | 不安が広がっている |
| 士気20〜39 | 不満が表面化している |
| 士気19以下 | 暴動の危険がある |

プレイヤーが数字を計算しなくても、町の状況を想像できることが重要。
