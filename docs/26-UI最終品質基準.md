# UI 最終品質基準

PR1〜PR10 で刷新・検証基盤を整備した Phaser Presentation 層の最終受け入れ基準を記録する。
この文書は旧 UI との互換性を定義するものではない。現行の単一 Presentation 構造だけを正とする。

## 1. 正とする画面構造

- 通常操作: `HudBar` + `TownLayer` + `CharacterDeck` + `PlanningControls`
- 人物選択: `CharacterFocus`
- 施設選択: `FacilityFocus`
- ターン結果: `FlowPresentation`
- 物語進行: `EventPresentation` / `ChoicePresentation` / `ArrivalPresentation` / `EndingPresentation`
- グローバル: `TitleScene` / `MenuPresentation`
- 表示モードの正: `PresentationDirector`

旧 `TrayLayer`、旧詳細パネル、旧計画ストリップ、旧一括 Overlay を互換目的で復活させない。

## 2. レスポンシブ契約

- wide: 論理サイズ `1280x720`
- narrow: 論理サイズ `480x854`
- 境界: viewport 幅 `900px`
- DPR は見た目の鮮明さにのみ影響し、論理レイアウトを変えない
- 同一 device class 内の viewport 変更でも再レイアウトする
- `viewport-fit=cover` 環境では safe-area を論理座標へ変換し、操作 UI と全画面 Presentation の双方で回避する

## 3. 入力契約

- クリックとタップで主要操作が成立する
- `PixelButton` の表示・ヒット領域は最小 `44x44` logical px
- `Escape` は最前面のメニュー、ログ、人物/施設フォーカスを閉じる
- reduced-motion でも情報量と操作経路を失わない
- DnD は補助経路であり、人物選択→施設選択のタップ経路を常に残す

## 4. ブラウザ回帰

`scripts/e2e.mjs` で最低限以下を保証する。

- Title / Menu の wide・narrow 表示
- CharacterFocus の再表示と Escape
- タッチによる人物選択
- Planning / FacilityFocus
- FlowPresentation の通常演出と reduced-motion
- playback 中の新規開始リセット
- セーブ→リロード→続きから
- DPR 1/2
- wide の中間 viewport と narrow の compact viewport
- narrow を含む全可視 `PixelButton` の 44px タッチターゲット
- deterministic Presentation FixtureからのEvent / Choice / Arrival / Ending単独表示
- Story系4画面のwide・narrow・reduced-motion・touch target
- 各主要状態の診断用スクリーンショット artifact

### 4.1 Presentation Fixture

`src/scene/testing/presentation-fixtures.ts` を主要Presentationの決定論的な再現元とする。

- `planning`
- `unit-focus`
- `facility-focus`
- `flow`
- `event`
- `choice`
- `arrival`
- `ending`
- `title`
- `menu`

fixtureはE2E bridgeから直接表示し、何日分ものゲーム進行やイベント抽選に依存させない。fixture都合のstateを`GameState`やセーブ形式へ追加しない。

### 4.2 Visual Regression

`npm run test:visual` は上記10状態をwide `1280x720`・narrow `480x854`で撮影し、`tests/visual-baselines/`の20枚と比較する。OS間のフォントラスタライズ差を色差閾値で除外した上で、差分が全画素の`0.3%`を超えた場合は失敗し、actualとdiffを`test-results/visual/`へ出力する。CIでは同ディレクトリをartifactとして保存する。

意図的なUI変更でbaselineを更新する場合は、次の順序を守る。

1. `npm run test:visual`を実行し、actual / diffで変化箇所を確認する
2. 変更が要件どおりであることをwide・narrowの両方で確認する
3. `npm run test:visual:update`でbaselineを更新する
4. baseline PNGをUI実装と同じPRに含め、画像変更としてレビューする
5. 再度`npm run test:visual`を実行し、比較がgreenになることを確認する

差分を確認せずbaselineだけを更新してCIを通さない。環境差による微小なアンチエイリアス差はpixel比較の閾値内で吸収し、閾値自体をUI変更の都合で緩和しない。

## 5. CI ゲート

PR を公開する前に `.github/workflows/ci.yml` と同じ順序を基準に確認する。

1. `npm ci`
2. `npm run typecheck`
3. `npm run lint`
4. `npm run format:check`
5. `npm test`
6. `npm run build`
7. Chromium の Playwright セットアップ
8. `npm run test:prod`
9. `npm run test:e2e`
10. `npm run test:visual`

PR9 以降、UI 改修で一時的な旧実装を残すことを品質対策とはみなさない。新しい要件に不要な旧構造は同じ変更内で削除し、単一の表示経路へ収束させる。fixtureとVisual Regressionは現行Presentationを保護するためのものであり、旧Presentation経路を互換目的で復活させる根拠にしない。
