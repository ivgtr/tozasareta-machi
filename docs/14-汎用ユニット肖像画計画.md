# 汎用ユニット肖像画計画

[グラフィック設計](./08-グラフィック設計書.md) と [ユニット設計](./12-ユニット設計.md) に基づき、ランダム加入者用の汎用肖像画セットを制作し、加入時に決定的に割り当てるための計画。画像制作とコード実装は別トラックとし、実装は別エージェントに委任する。

---

## 0. 進め方の原則

- **先にアセット契約を固定**: ID、寸法、パレット、構図を合意してから生成する。
- **A/B は外見バリエーション**: 男女の描き分けに使うが、ゲームデータに性別属性は追加しない。
- **ゲーム上はフラットな8枚プール**: テーマと適性・特性は連動させず、すべて同確率で候補にする。
- **見た目の乱数でゲームを変えない**: 肖像選択は既存の `RngState.counter` を進めず、シードとユニットIDから派生させる。
- **重複を後回し**: 未使用肖像がある間は現在のロスターと重複させない。全枚使用中のときだけ再利用を許可する。
- **ゲート制**: 1マイルストーン = 1コミットを原則とし、画像の承認前に実装に着手しない。

### 非目標

- ユニークユニットの肖像差し替え
- 性別、年齢、出身、人種などの新規ユニット属性
- 肖像による適性・特性・バランスの変更
- 画像内の名前、役割ラベル、UI枠、アイコンの描画

---

## 1. アセット契約

### 1.1 肖像プール

| テーマ | A | B | 共通要素 | 差し色 |
| --- | --- | --- | --- | --- |
| 作業着 | `recruit_workwear_a` | `recruit_workwear_b` | 防寒作業着、汚れた襟元 | amber `#ffc857` |
| 整備・技術 | `recruit_utility_a` | `recruit_utility_b` | 厚手の上着、ゴーグルまたは工具の気配 | cyan `#6fd8ff` |
| 救護・世話役 | `recruit_care_a` | `recruit_care_b` | スカーフ、エプロン、簡素な救護服 | green `#5ee6a8` |
| 町の住民 | `recruit_townsfolk_a` | `recruit_townsfolk_b` | コート、帽子、避難者らしい着込み | gold `#ffd94a` |

- 配置先: `src/ui/assets/portrait/{id}.png`
- 完成サイズ: **48×48 PNG**（08 §3.2 の既存肖像スロットを維持）
- 背景: 不透明の濃紺。透過処理は行わない
- 色: `#0a0e24 #131740 #1c2258 #e8ecff #ffc857 #ff5f66 #5ee6a8 #6fd8ff #ffd94a` の9色以内
- 形式: indexed PNG、4-bit colormap、アンチエイリアスなし

### 1.2 構図の固定条件

- 胸上、正面または全員共通の軽い3/4向き
- 頭頂、目線、肩、顎の位置を8枚で揃える
- 表情は「疲れているが、断固としている」
- 夜の左上光源、右下に深い影を共通化する
- A/B は同テーマの服装記号を共有し、顔輪郭、髪型、首元で判別できるようにする
- 小サイズ表示を優先し、工具や服の細部を詰め込みすぎない

## 3. R1–R2 画像制作手順

1. 既存の背景・イベント画像をパレットとディザリングの参照として確認する。
2. built-in image generation を使い、`recruit_workwear_a` を単独で生成する。
3. 構図、表情、小サイズでの認識性を修正し、基準画像を固定する。
4. 基準画像をスタイル参照とし、`recruit_workwear_b` を生成する。
5. R1 のゲート通過後、残り6枚を**1アセット1生成コール**で制作する。
6. 生成結果を近傍法で48×48へ縮小し、固定パレットへ量子化する。
7. 8枚を同じ倍率で並べて目視確認し、採用品のみを `src/ui/assets/portrait/` に配置する。
8. 各ファイルの寸法、カラータイプ、色数を機械確認する。

### 3.1 共通プロンプト

```text
Use case: stylized-concept
Asset type: 48x48 in-game unit portrait for a retro disaster-management game
Primary request: Create one generic recruit bust portrait for an isolated small town during a prolonged disaster.
Scene/backdrop: Flat opaque dark navy background, no scenery.
Subject: One adult town resident, tired but resolute, wearing {theme details}; visual variant {A or B}.
Style/medium: 16-bit pixel art, visible dithering, crisp hard pixel edges, no anti-aliasing.
Composition/framing: Square bust portrait, consistent head size and eye line, centered shoulders, slight three-quarter view.
Lighting/mood: Sparse cold night light from upper left, deep shadow, restrained and serious.
Color palette: Use only #0a0e24 #131740 #1c2258 #e8ecff #ffc857 #ff5f66 #5ee6a8 #6fd8ff #ffd94a; emphasize {accent color}.
Constraints: One person only; readable at 32px; match the approved reference portrait's framing, pixel density, lighting, and background.
Avoid: text, letters, numbers, UI frame, badge, emblem, watermark, scenery, modern fashion, photorealism, smooth gradients, soft edges.
```

生成プロンプトの `{theme details}`、`{A or B}`、`{accent color}` だけを各アセットで変更する。画像制作上は A を masculine-presenting adult、B を feminine-presenting adult と指定するが、この区別はプロンプトとファイルIDのみに留める。構図と光源は変えない。

### 3.2 画像ゲート

- [ ] 8枚が48×48の不透明PNG
- [ ] 使用色が指定9色の範囲内
- [ ] 4テーマが32px表示でも区別できる
- [ ] 各テーマのA/Bが服装の一貫性を保ちつつ判別できる
- [ ] 頭部サイズ、目線、肩位置、光源が揃っている
- [ ] テキスト、UI、透過、未指定色、滑らかな勾配がない
- [ ] 既存のシーン・イベント画像と同じ作品世界に見える

## 4. R3 決定的割り当て設計

### 4.1 定数と関数契約

`src/game/data/units.ts` に8枚の固定配列を定義する。配列順はセーブ互換性の一部とし、公開後は並べ替えない。

```ts
export const RANDOM_PORTRAIT_IDS = [
  'recruit_workwear_a',
  'recruit_workwear_b',
  'recruit_utility_a',
  'recruit_utility_b',
  'recruit_care_a',
  'recruit_care_b',
  'recruit_townsfolk_a',
  'recruit_townsfolk_b',
] as const
```

選択は、概念上次の純粋関数に分離する。

```ts
selectRandomPortrait(seed: number, unitId: string, usedPortraits: readonly string[]): RandomPortraitId
```

- `usedPortraits` を除いた候補があれば、その候補のみから選ぶ
- 候補が空なら全8枚を復活させる
- `seed + unitId` を安定ハッシュし、候補数の範囲に写像する
- `Math.random` を使わない
- `RngState.counter` を進めない
- 同一入力に対し必ず同一IDを返す

### 4.2 加入ロジック

`makeRandomUnit` に現在使用中の肖像ID群を渡し、既存の `portrait: recruit_${counter}` を選択済みIDに置き換える。

```ts
makeRandomUnit(
  rng: RngState,
  takenNames: readonly string[],
  usedPortraits: readonly string[],
): { unit: Unit; rng: RngState }
```

`events-data.ts` は `state.units.map((unit) => unit.portrait)` を渡す。肖像は加入時に一度だけ選び、結果を既存の `Unit.portrait` に保存する。`Unit` 型に新しいフィールドは追加しない。

### 4.3 名前とA/Bの関係

現行の名前生成と肖像選択は独立させる。名前から性別を推定したり、A/Bを合わせたりしない。これは「性別データを持たない」という仕様上の意図的な結果とする。

## 5. R4 UI・セーブ互換性

### 5.1 アートマニフェスト

`src/ui/art/manifest.ts` に8枚を登録する。実画像の自動検出には必須ではないが、`alt`、プレースホルダ、開発時の識別名を安定させるため登録する。A/Bを男女と読み上げるラベルは避け、「汎用加入者・作業着A」のようにする。

### 5.2 実画像の表示寸法

現状のCSSはプレースホルダの寸法指定が中心のため、実際の `<img>` にも同じサイズ契約を適用する。

| 表示箇所 | 目標寸法 |
| --- | --- |
| ランダム加入スポットライト | 56×56 |
| 通常ユニットカード | 44×44 |
| コンパクトカード | 32×32 |
| ユニット詳細 | 現行コンポーネントの正方形枠に追従 |

- コンテナに `width` / `height` / `aspect-ratio: 1` を明示する
- コンテナ内の `.pixel-art` は `width: 100%; height: 100%`
- `object-fit: cover` と `image-rendering: pixelated` を維持する
- プレースホルダと実画像でレイアウトを変えない

### 5.3 旧セーブの正規化

`Unit` スキーマは変わらないため、`SAVE_VERSION` は引き上げない。`parseStore` の検証後に、次の条件を満たす肖像だけを正規化する。

- `unit.id` が `recruit_` で始まる
- `unit.portrait` が新しい8枚プールに含まれない

`history` の古いスナップショットから現在の `state` まで時系列順に処理し、`unit.id → portrait` の一時マップを共有する。同じユニットが別スナップショットに現れたら最初の割り当てを再利用し、undoで肖像が変わらないようにする。正規化はRNGを消費せず、次回保存時に新しいIDが自然に永続化される。

## 6. テスト・検証計画

### 6.1 単体テスト

- 同じ `seed / unitId / usedPortraits` で同じ肖像IDが返る
- 返値が必ず `RANDOM_PORTRAIT_IDS` に含まれる
- 未使用候補がある間は使用中IDを返さない
- 8枚すべて使用中でも有効なIDを返す
- 肖像選択の前後で `RngState.counter` の進み方が変わらない
- ランダムユニットは動的 `recruit_<counter>` を肖像IDに使わない
- 旧 `recruit_<counter>` 肖像を含むセーブが読み込め、state/historyの両方が正規化される
- serialize → parse 後も割り当て肖像が変わらない

### 6.2 統合・表示確認

- ランダム加入でプレースホルダではなく実画像が表示される
- 加入オーバーレイを閉じた後も同じ肖像がカードに表示される
- undo、ページ再読み込み、再開で肖像が変わらない
- 56/44/32px で顔が潰れず、レイアウトシフトが発生しない
- デスクトップとモバイルの両方でスポットライトが画面内に収まる
- ユニークユニットのプレースホルダ表示は壊れない

### 6.3 品質コマンド

```text
npm run format:check
npm run lint
npm run typecheck
npm test
npm run build
npm run sim
npm run playwright
```

simulation の同一シード結果が実装前後で一致することを確認する。肖像割り当てを理由にバランス数値を調整しない。

## 7. リスクと対策

| リスク | 影響 | 対策 |
| --- | --- | --- |
| AI生成ごとに構図がぶれる | 高 | R1で基準ペアを固定し、全プロンプトで参照画像と固定条件を再掲 |
| 48px化で顔やテーマが潰れる | 高 | 小サイズのシルエットを優先、32pxプレビューをゲート化 |
| 肖像追加でゲーム乱数列が変わる | 高 | 派生ハッシュを使い `RngState` を消費しない、simを実装前後で比較 |
| 同じ肖像が並び個体識別しにくい | 中 | 現在のロスターの未使用肖像を優先、プール枯渇時だけ再利用 |
| 名前とA/Bの印象が一致しない | 中 | 仕様として独立抽選を明記、ゲームデータへ性別を添加しない |
| 実画像だけCSS寸法が変わる | 中 | コンテナ寸法を明示し、プレースホルダと `<img>` を同条件でテスト |
| 旧セーブでプレースホルダに戻る | 中 | state/historyの旧動的IDを読み込み時に決定的に正規化 |

## 8. DoD

- [ ] 旧セーブとundo historyの動的肖像IDが安全に正規化される

## 9. 実装エージェントへの引き継ぎ

R3 着手時に、実装エージェントは次の順で確認する。

1. 本計画書と08 §3/§7、12 §10を読む。
2. R2の8画像とファイルIDが確定済みか確認する。
3. 作業開始時の `git status` を確認し、他者の変更を保存する。
4. R3とR4を別コミットで実施する。
5. 画像の再生成やユニーク肖像への拡張は行わない。仕様上の疑義がある場合は、実装前に計画書を更新する。
